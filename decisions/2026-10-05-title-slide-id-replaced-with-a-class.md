## 2026-10-05 — The title slide's id is replaced with a class

**Context:** Opening the presentation changed the address bar from `.../deck/` to `.../deck/#/title-slide`, breaking a plain copy-pasted URL. reveal.js's Location plugin (`getHash` in `style/revealjs/dist/reveal.js`) builds the URL hash from the *current slide's `id` attribute* — a slide with an id always gets `#/<id>`, and only an id-less slide at indices `h=0, v=0` gets the bare `/` that the deck's own `history.replaceState` call (`style/body-controls.html`, written on `visibilitychange`) and reveal.js's own `writeURL` both special-case into a hash-free URL. Pandoc's revealjs writer gives the deck's own title slide `id="title-slide"` and nothing else, so it never qualified for that bare-`/` case once shown.

**Decision:** `rename_title_slide_id` (`lib/build_helpers.rb`) strips that id and adds `class="deck-title-slide"` instead, as the very first step of both `post_process_index` and `post_process_print` — before any other post-processing step, CSS rule or JS selector ever sees the markup. A bare `title-slide` class was rejected: Pandoc already stamps a `title-slide` class on *every* level-1 section (each song's own title sub-slide), so reusing it would make the deck's cover indistinguishable from a song's title slide in CSS/JS. Every selector that targets this slide was moved from `#title-slide` to `section.deck-title-slide` — the element type is required, not optional: reveal.js copies a slide's classes onto its separate `.slide-background` div too, so a bare `.deck-title-slide` would silently also match that background div (which is a `<div>`, never a `<section>`).

**Reasoning:** Two alternatives were rejected. Patching the vendored `getHash` so slide 0 always returns `/` regardless of id was rejected because the project doesn't otherwise patch vendored reveal.js, and the patch would also affect any future deck that *does* give slide 0 an id for a legitimate reason. `hash: false` was rejected outright — reloading would no longer restore the current slide, which is the entire point of `hash: true` plus the custom `visibilitychange` writer. Removing the id instead of patching the library fixes the root cause (an id-bearing slide at index 0) rather than special-casing around it, and generalizes: any other id-less slide at `h=0, v=0` already gets the same hash-free treatment for free.

One non-obvious fallout: two places in the code looked slides up *by id* and silently misbehaved once the title slide's id was gone. `style/slide-zoom.js`'s `fitSlide` checked `section.id === 'title-slide'` to decide whether to apply the zoom-to-fit behaviour — changed to `section.classList.contains('deck-title-slide')`. More subtly, `style/body-controls.html`'s `onSong()` (gates whether 🚀 is shown) used a `NON_SONG_SLIDES` map keyed by id, with `'title-slide'` as one of three entries (the others, `TOC` and `introduction`, keep their ids); looking up an id-less slide there returns `undefined`, which made `onSong()` wrongly report *true* — 🚀 would have appeared on the title slide. Fixed with an explicit `stack.classList.contains('deck-title-slide')` check ahead of the id-based map, rather than trying to shoehorn a class into a map keyed by id.

A second trap, caught before it shipped rather than after: `style/serif.css` carries `#title-slide h1, #title-slide p.author { color: black; text-shadow: ... }`, needed so the title text stays legible over the print theme's background image. The vendored theme itself sets `.reveal h1 { text-shadow: var(--r-heading1-text-shadow) }` (effectively `none`) at `.reveal`-class-plus-element specificity, and — because that vendored `<link>` is emitted *after* this project's own inline `<style>` block in the generated HTML — it would win any specificity tie. The old id selector always out-ranked it regardless of document order; a naive `.deck-title-slide h1` would have tied with it and *lost* on source order, silently dropping the shadow. Fixed by keeping an extra `.reveal` class in the selector (`.reveal .deck-title-slide h1, .reveal .deck-title-slide p.author`), which isn't a hack — `.reveal` genuinely is an ancestor of this slide — just enough extra specificity to win outright instead of relying on cascade order.

A third trap broke the whole browser suite, not just the title slide, and took the longest to find because the symptom pointed nowhere near this change: after the fix, every browser spec started failing with `Ferrum::TimeoutError` on the very first `evaluate_script` after `visit` — pages that have nothing to do with the title slide (`mobile_spec.rb`, `chord_tooltips_spec.rb`, `toc_filter_spec.rb`) failed identically. Tracing it with raw CDP network/initiator logging (bypassing Capybara) showed four of the five `<script src="/style/…">` tags being fetched *twice* — once correctly, once as `http://spec/style/….js`, `net::ERR_NAME_NOT_RESOLVED`. "spec" is the first path segment of `FixtureBuilder::URL_PATH` (`/spec/fixtures/index.html`). The cause: every spec sets `Capybara.app_host = FileServer.url` with no argument, and the old `FileServer.url` always appended a trailing `/` even for an empty path; Capybara's `Session#visit` builds the final path as `base_uri.path + visit_uri.path` — plain string concatenation, not a slash-aware join — so the two leading slashes (one from the host, one from `URL_PATH`) doubled up into `location.pathname == "//spec/fixtures/index.html"`. That was harmless for as long as nothing ever fed `location.pathname` back into a URL constructor, which is exactly what both this project's own `visibilitychange` handler and reveal.js's vendored `Location` plugin do on the *bare-`/`* branch: `history.replaceState(null, '', location.pathname + location.search)`. A string that starts with `//` is a network-path reference — the browser throws away the current scheme+host and treats the next segment as the new host, so the document's effective origin silently became `http://spec`, and every absolute-path (`/style/…`) request made after that point resolved against the wrong origin and failed DNS resolution. Before this fix, that branch was dead code: `getHash()` never returned bare `/` while the title slide carried an id, so the double slash sat there inert since whenever this suite was written. Fixed in [file_server.rb](../spec/support/file_server.rb): `FileServer.url` with no argument now returns the bare origin, no trailing slash, so `base_uri.path` is `""` and Capybara's concatenation produces a single leading slash like it should have all along. Vendored reveal.js was deliberately left alone — the bug is in how the test harness builds its own URL, not in the library, and production serves the deck from a real root path with no double slash to trigger this in the first place.

Tested in [rename_title_slide_id_spec.rb](../spec/unit/rename_title_slide_id_spec.rb) (the id-to-class swap itself, including idempotency), [golden_html_spec.rb](../spec/integration/golden_html_spec.rb) (the id is gone from the generated markup, pinned via the golden fixture), and [index_html_spec.rb](../spec/browser/index_html_spec.rb) (a real browser round-trip: no hash on load, `#/TOC` after navigating off the title slide, hash-free again navigating back — this example is also what exercises the bare-`/` `replaceState` branch and would catch the `file_server.rb` regression above if it ever came back).
