## 2026-11-11 — Guests wish for songs with a ❤️, counted per session by every device

**Context:** The host picks the next song by feel. The guests wanted a say: a ❤️ on each song — in its row of the table of contents and on its title slide — that anyone can press, with a count of how many want it, so the host sees what the room is in the mood for. The count had to be shared live across the room, and it had to be per evening: one does not have the same taste every night. The song book is a static page plus a relay with no storage, so there is nowhere to keep a count but the devices themselves.

**Decision:** A wish is a session feature. In a session, every device shows the hearts (`body.wishes-active`); outside one they stay hidden, since there is no room to count. A press toggles this device's wish (not a one-way +1: a mistap must be undoable), and the count beside the heart is the number of devices in the session that currently wish the song. The wishes travel on a fifth message type, `wish`, on the one relayed event, and **every device tallies them itself**: each sends its whole set of wished songs — on every change, on connect, and again every round (8 s) while it has any — and each keeps the sets it hears, per sender, dropping a sender unheard for three rounds. A device's own wishes are stored with the session and go with it when it is left or ended; the next evening starts from none.

**Reasoning:**

- *Per session, not for all time.* A persistent all-time counter would need a server with storage, which this project deliberately does not have (the relay forwards and forgets), and it would answer the wrong question: what the room wants tonight, not what was popular last month. Tying the wishes to the session gives the reset for free — the channel is `sha256(secret)`, so only this evening's devices hear each other, and leaving the session forgets them.
- *A peer tally, not the host as authority.* Everything else in a session has the host as the single authority, and the first draft had the host collect the wishes and carry the counts in its heartbeat. But the wishes come *from* the guests, and the host would have had to be told about every guest's set again whenever it took over, reloaded or reconnected — a claim/epoch dance for no gain. Letting every device tally what it hears makes a takeover and a host reload non-events: the new host has been hearing the same `wish` messages all along. The host's heartbeat stays as it was.
- *Whole sets, repeated, not deltas.* A `+1`/`−1` message that is lost leaves the count wrong for the rest of the evening. A device's whole set, sent again every round, is idempotent: one lost packet costs a round, nothing more, and a latecomer is counted, and counts everyone, within one round. A sender unheard for three rounds has closed its tab: its wishes lapse, where a delta model would have counted them till morning.
- *Hidden outside a session.* A heart that counts nothing would be a lie or a private bookmark; the user chose the shared count, so the heart appears with the session. The markup is built in regardless (the golden fixtures pin it); only the class shows it.
- *The title slide too.* Browsing the book, one is as often on a song as on the list; the same button, under the same slug, stands in both places, and `wishes.js` renders both from one state.
