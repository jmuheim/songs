## 2026-10-01 — The multiplex token is generated locally, not fetched

**Context:** `build` fetched the `socketId` / `secret` pair once from `https://multiplex.up.railway.app/token` and cached it in the committed `multiplex-token.json`. Because the file was committed and shared, every build — including a local one — used the same pair as songs.josh.ch. So a local build broadcast on the live channel, and local testing could move real listeners' slides.

**Decision:** The pair is generated offline — the relay only verifies `sha256(secret) == socketId`, so any self-consistent pair works and no network call is needed. `build` resolves it as: `MULTIPLEX_SOCKET_ID` + `MULTIPLEX_SECRET` from the environment first (the CI deploy generates a fresh pair per run that way), else a **gitignored** `multiplex-token.json` created with `bundle exec rake multiplex:token`, else it **aborts with a clear message** — no silent fall back to the network. The committed `multiplex-token.json` was removed. The generator is `BuildHelpers.generate_multiplex_token`, shared by the rake task.

**Reasoning:** Generating offline removes the only reason `build` ever touched the network and, more importantly, gives every machine its own session, so local work can never disturb the live channel. Passing the pair in the environment lets CI mint a throwaway pair per deploy without a file. Aborting when the pair is absent — rather than fetching one — keeps the failure loud and the "never touch the live channel" guarantee intact. The file kept its `multiplex-token.json` name and JSON shape (rather than a `.env`) because `build` already parsed it and the specs are unaffected — they keep their own fixed test pair in `spec/support/multiplex_server.rb`. Pattern taken from axipedia's `build/setup_env.rb` and its deploy workflow.
