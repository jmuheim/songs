## 2026-10-03 — `.htaccess` sends cache headers so phones stop showing stale builds

**Context:** People following along on their phones sometimes saw an outdated song book after a deploy. `index.html` and `style/*.css|js` keep the same filename on every deploy, and the server sent no `Cache-Control` header, so browsers fell back to heuristic caching — a cached copy never looks stale to the browser on its own. This bites hardest on phones: iOS Safari's "Add to Home Screen" bookmarks run in a webview that caches even more aggressively than a normal tab, so a song book added to the home screen could keep showing a build from weeks ago.

**Decision:** Ship a root `.htaccess` with every deploy (added to the rsync file list in `build` and `.github/workflows/test.yml`, alongside `index.html` and `style/`). It sets `Cache-Control: no-cache, must-revalidate` on `.html`/`.css`/`.js`, and `public, max-age=31536000, immutable` on fonts.

**Reasoning:** `no-cache` still lets the browser keep a local copy; it just forces a conditional request on every load, so an unchanged file comes back as a cheap 304 and a changed one as a fresh 200 — no round-trip tax beyond that, which is negligible for a song book this size. Fonts and the vendored reveal.js/qrcodejs builds never change between deploys, so forcing them through the same revalidation would just be wasted round trips; they get the long-lived `immutable` cache instead. Query-string cache-busting on the asset URLs was considered and rejected as a partial fix: it would solve staleness for `style/*.css|js`, but `index.html` itself — the file that contains those URLs — would still be subject to the browser's heuristic caching, so a stale `index.html` would keep pointing at a stale asset version anyway. The server-header approach (relying on Uberspace's Apache and `mod_headers`) fixes the root file too, with no change to the build pipeline's markup.
