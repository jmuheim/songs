## 2026-10-04 — Reorganize on-screen controls into four corners, each behind a dialog where there's more to say

**Context:** 📖, 🎹, 🔗, 🚀 and 🌞 had accumulated as five always-visible standalone buttons across the two top corners, plus a floating `#multiplex-status` text line — cluttered even when most of them were irrelevant to the moment (🚀 sat there, merely greyed out, on the title slide and the TOC; the status line only ever said anything during a live-scroll session). The user asked for a tidy-up: one control per corner, each doing one job, with a dialog behind it for anything that needs more than an icon can say. They pointed at the sibling project `axipedia`'s "pill + dialog" pattern (`revealjs/assets/deck-settings.js`, and its multiplex "lamp" in `revealjs/plugin/multiplex/multiplex.js`) as the model to borrow.

**Decision:** Four corners, one control each: top-left 🔗 QR then 📖 TOC (TOC hidden while a live-scroll session locks this device's navigation), top-right ⚙️ Settings (a dialog holding the theme `<select>` — Dunkel/Hell — and an "Akkorde anzeigen" checkbox, replacing the standalone 🌞 and 🎹 buttons), bottom-left a graphical multiplex status button, bottom-right 🚀 (now *hidden*, not merely disabled, off a song — `master-mode.hidden = !onSong()` instead of `.disabled`). The status button is **role-aware**, not just connected/disconnected: a filled dot when this device drives the scroll (self-scroll presenter or a guest scrolling for the room), an open ring when it's locked to someone else's scroll instead (an ordinary follower, or the presenter after delegating to a guest), amber while a presenter waits for a guest to volunteer, grey when idle, and a diagonal strike over whichever shape applies when the socket is disconnected — shape plus colour, never colour alone (WCAG 1.4.1), mirroring axipedia's own reasoning for its master-dot/client-ring lamp. A click opens a dialog with the same state spelled out in words; the old `#multiplex-status` id survives, just relocated onto a `.visually-hidden` span inside the button (still `role="status"`), so it keeps working as both the button's accessible name and a screenreader-announced live region.

**Reasoning:** A plain connected/disconnected dot was considered and rejected in favour of the richer role-aware version — asked of the user directly, who confirmed axipedia's fuller approach was the intent, not a stripped-down traffic light. Hiding 🚀 instead of disabling it was chosen because "only visible when a song is shown" was explicit in the request, and a session is never active while off a song anyway (the scroller can't leave it, followers are snapped to it), so `!onSong()` alone correctly covers both the inactive and active cases without a separate `disabled` state to track. The TOC link is hidden during a session (not just left clickable and relying on the existing `slidechanged` snap-back) because the snap-back only fires *after* the jump, producing a visible flash back to the TOC and back again — hiding the control avoids the flash entirely, the same reasoning `SCROLLER_KEYS` already applies to the keyboard. Settings dialog text and corner-button tooltips split language the same way the rest of the UI already does: dialogs in German (matching `master-modal`, `qr-modal`, the scroll-choice/invite/announce dialogs), tooltips in English (matching 📖/🎹/🔗/🌞 historically). One bug surfaced along the way: giving `#master-mode` a `hidden` attribute didn't hide it, because `.ctrl { display: inline-flex }` — equal specificity to the UA stylesheet's `[hidden] { display: none }`, but declared later in the cascade — won out; fixed with an explicit `.ctrl[hidden] { display: none }` rule. A second bug: the settings dialog's wiring ran as an immediately-invoked function reading `#theme-select` etc. by id, but that markup sits *after* the script tag in the document — `getElementById` returned `null`, threw, and silently aborted the rest of that `<script>` block, including unrelated tooltip-hover wiring further down the same tag. Fixed by deferring the DOM-dependent part of that IIFE to `window.addEventListener('load', …)`, consistent with how every other dialog in `body-controls.html` is already wired.
