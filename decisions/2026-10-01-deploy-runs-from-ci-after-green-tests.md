## 2026-10-01 — Deploy runs from CI after green tests, not on every save

**Context:** `./dev` called `./build --deploy` inside its fswatch loop, so every intermediate local save went live to songs.josh.ch — untested, straight from a working tree. There was no gate between "typing" and "published".

**Decision:** `./dev` now builds locally only (no `--deploy`). A `deploy` job was added to `.github/workflows/test.yml`: it runs **only on a push to `master`**, **after** the `rspec` job (`needs: rspec`, so a red suite blocks it), in its own `concurrency` group so two pushes deploy in sequence rather than racing. It generates a fresh multiplex pair, runs `./build`, and `rsync --delete`s `index.html` + `style/` to the server — the same files the old manual deploy sent (`print.html` stays out). `MASTER_PASSWORD` keeps its `guitar` default in CI. `./build --deploy` remains the manual fallback, using the developer's own SSH access.

The server is reached with a dedicated ed25519 key (secret `DEPLOY_SSH_KEY`), **not** anyone's personal key, locked on the server through `authorized_keys` (`command="…/rrsync /var/www/virtual/maroni/songs.josh.ch",restrict`) so it can only rsync into that one directory — which makes the rsync target relative. The host key is pinned in the workflow (no `StrictHostKeyChecking=no`).

**Reasoning:** Deploying only after a green run means a broken deck can't go live; keying it to `master` keeps the trigger obvious. A deploy-only key, scoped to the single web directory, limits what a leaked secret could touch — far less than a personal key with full shell access. `rrsync` was confirmed present on Uberspace (shipped with rsync 3.1.2 at `/usr/share/doc/rsync-3.1.2/support/rrsync`, with perl available), so the restriction was feasible; had it been missing, the fallback was an unrestricted key only with the maintainer's agreement. Pinning the host key rather than disabling the check means a man-in-the-middle can't redirect the deploy. The maintainer owns the out-of-band half (generating the key, the `authorized_keys` line, `gh secret set DEPLOY_SSH_KEY`). Workflow shape adapted from axipedia's `deploy.yml`.
