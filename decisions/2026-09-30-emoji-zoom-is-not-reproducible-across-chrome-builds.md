## 2026-09-30 — Emoji zoom is not reproducible across Chrome builds

**Context:** With the specs now running in CI ([CI runs the specs on every push](2026-09-30-ci-runs-the-specs-on-every-push.md)), two browser examples failed on the Linux runner though they pass on macOS. One was the slide-zoom example: it pins the title slide's exact `zoom` (reveal.js computes zoom from the rendered content size), and the title slide carries emoji (`🔥🎶🌛`, `😊 … ❤️`). The runner's Chrome laid them out differently from macOS Chrome (`1.47977` vs `1.41436`), so the exact value did not match. The pure-text slides (the verse at `0.763268`, the clamp-to-`1` case) matched exactly on both.

We first tried to remove the difference by bundling the emoji as a webfont (a subset of Noto Color Emoji) and forcing every device to draw them from it — the way the text fonts are already bundled. That made the emoji *style* identical everywhere and surfaced a real bug (the zoom was computed before the async fonts loaded), but the title zoom *still* differed across the two Chromes (`1.57248` vs `1.47977`) with the font loaded: Chrome's colour-emoji layout is not stable across its own builds. So the bundling was reverted — it changed the look (Noto instead of Apple emoji, for the author too) without buying determinism — and only the font-load fix was kept.

**Decision:** The title slide's zoom is asserted exactly only off CI; on CI (`ENV['CI']`) the example checks that a plausible zoom (`1.3..1.7`) was applied. The text-only verse and clamp values stay exact everywhere. Independently, `style/slide-zoom.js` now re-fits the current slide on `document.fonts.ready`, so a slide first painted before its web fonts arrive is corrected once they load — a real fix for slow connections, not just for the specs. (The other CI failure, the control tooltip, was unrelated: it is gated on `matchMedia('(hover: hover)')`, which the runner's headless Chrome reports false and CDP cannot emulate, so that spec now simulates a hover-capable pointer by patching `matchMedia` before the page's scripts run.)

**Reasoning:** The exact zoom exists to catch a font that renders differently; it can still do that for the text fonts, which are bundled and lay out identically everywhere. Colour emoji are the one thing we cannot pin cross-build, and the only ways to force it — bundling identical Chrome versions, or dropping the emoji from the title — cost more than the check is worth. Range-checking the title on CI keeps the example running there (it still catches "zoom not applied" or a gross layout break) while the exact figure keeps its full value on the machine the book is actually authored on. Keeping the emoji as the OS draws them means macOS still shows Apple emoji, as before.
