## 2026-10-04 — CI's `push` trigger is scoped to `master` only

**Context:** [CI runs the specs on every push](2026-09-30-ci-runs-the-specs-on-every-push.md) set up `on: push` (any branch) alongside `on: pull_request`, deliberately unscoped since Actions minutes are free on a public repo. In practice, every commit pushed to a branch with an open PR fires both events — `push` and `pull_request` — running the identical `rspec` job twice per commit, visible as two separate, simultaneous "Tests / rspec" checks on the PR.

**Decision:** `push` is now scoped to `branches: [master]`; `pull_request` stays unscoped (it already covers every branch once a PR is open). `master` still needs its own `push` trigger, separate from `pull_request`, because the `deploy` job's `needs: rspec` depends on an `rspec` run from that *same* push-triggered workflow run — merging a PR doesn't re-fire `pull_request` (only `opened`/`synchronize`/`reopened` do by default, not `closed`), so without a `push` trigger on `master` the merge commit would never get an `rspec` run for `deploy` to hang off.

**Reasoning:** The original "free minutes, no reason to gate" reasoning still holds for *coverage* — nothing goes untested. What it didn't account for is pure duplication: a PR branch gets full coverage from `pull_request` alone, so the matching `push` run on every commit added nothing except running the same suite a second time and a second, redundant check in the PR's list. Branches without an open PR yet lose their push-triggered run under this change — a deliberate tradeoff, accepted because this repo's actual workflow is branch-then-PR-promptly, not long-lived unreviewed branches sitting untested for a while.
