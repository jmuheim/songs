## 2026-10-01 — Build outputs are not committed

**Context:** `index.html`, `print.html`, `all-songs.md` and the fixture copies `spec/fixtures/index.html` / `print.html` were committed build outputs. Every rebase and merge conflicted on them, and they drifted from source — the previous song commit left `all-songs.md` stale, which `build_output_spec` (it compared the committed `all-songs.md` against a fresh regeneration) only caught after the fact. `tmp/all-songs.md` and `tmp/print.html` were long-untouched leftovers.

**Decision:** Those five files are now generated, not committed — `git rm --cached` plus `.gitignore`. `./build` writes them, the specs rebuild the fixture HTML at the start of a run, and CI rebuilds them for the deploy. The `tmp/` leftovers were deleted. The golden snapshots under `spec/fixtures/golden/` stay committed — they are the hand-curated reference the golden specs diff against. `build_output_spec.rb`, whose comparison no longer had a committed file to check, was repurposed: it now asserts that the **real** `content/songs/` compiles — every song passes `validate_song!`, and `songbook_markdown` concatenates the front matter, the introduction and every song with chords marked up.

**Reasoning:** The outputs are fully reproducible from source, so committing them bought nothing but merge conflicts and drift. Keeping only the golden fixtures committed keeps the one thing that *is* a reference (what the HTML should look like) under review, while the bulky derived files stay out. The old spec's real purpose — "someone forgot to rebuild" — disappears once the file isn't committed; replacing it with a real-content build check keeps a guard in CI that nothing else had (the golden specs build the fixture songs, not the actual repertoire), so a malformed song fails before it can reach a deploy.
