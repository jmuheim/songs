# Songs browser specs — conventions

The browser specs drive headless Chrome through Capybara → Cuprite → Ferrum → CDP. **Solve each step at the highest level that works, and justify any drop below Capybara with a comment.** Injected JavaScript (`evaluate_script`) is the last resort — it skips Capybara's waiting and hides intent.

## Reach for the waiting layer first

- **Capybara matchers and actions** wait and retry: `have_css` / `have_no_css` / `have_text` (with `text:`, `count:`, `visible: :all/:hidden`), `find`, `click`, `hover`, `click_button`, `click_link`. The custom `have_visible` matcher is in `spec/spec_helper.rb`. Prefer these over reading the DOM yourself.
- **For state Capybara can't see** — Reveal's indices, an inline `style="transform: scale(…)"`, `document.activeElement` — poll with the helpers already in `spec/spec_helper.rb`: `wait_for_reveal`, `wait_for_js(condition)`, `press(*keys)`, `active_element_id`. Never a fixed `sleep`.
- **`press` types into whatever has focus** (`keyboard.type`). Do **not** use `send_keys` on a node to test key handling: Cuprite clicks the node first, which moves focus — `press` exists precisely to avoid that.
- Drop to `page.driver.browser.mouse` / `.page.command('…')` (raw CDP) only for what Ferrum/Capybara can't express, and say why at the call.

## Extend before you add

`capybara/rspec` resets the session around every example, so each one re-visits and re-runs Reveal's init — a deck load costs roughly a second, an extra assertion on an already-loaded page costs nothing. So **look for an example that already loads the right page and add to it**:

- Group by page state (one example per URL × mutation). Fold pure reads of the same page into one example wrapped in `aggregate_failures`, with a comment per assertion carrying what a separate example's name would have said.
- A new example earns its keep only with a new page state — a different URL, or a mutation (click, key, injected class) a later read must not see. Otherwise fold it into the neighbour.
- Don't let a `before { load_presentation }` run for an example that then navigates away — split that example into a sibling `describe` without the hook.

## Make a new check able to fail

A spec that stays green whether or not the behaviour works is worthless. After writing one, break the behaviour locally (comment out the handler, change the value) and confirm the spec goes red. This is the bar for every assertion, not just browser ones.

## Traps that have bitten here

- **The mouse stays where it last clicked or hovered.** After a click the pointer sits on that element, so keys pressed next land on its hover state (e.g. dismiss its tooltip, or page the deck). Move it away first — `page.driver.browser.mouse.move(x: 640, y: 500)` — before a keyboard sub-test. See the 🎹 toggle example in `index_html_spec.rb` ("The mouse leaves first: keys pressed while it rested on 🎹 dismissed its tooltip").
- **`slide-zoom.js` scales each slide with a transform, so CSS px are not screen px.**
  - **Two measures:** `getComputedStyle` gives the unscaled CSS values (a chord's font size, an outline's width), and `getBoundingClientRect` gives the scaled box on screen. Divide one by the other for a slide's scale (`rect.height / el.offsetHeight`, as `chords.js` does).
  - **What to assert:** the **colour and style**, not pixel widths — `getComputedStyle(el).outlineStyle + ' ' + outlineColor` → `'solid rgb(255, 255, 255)'` in `chord_tooltips_spec.rb`. Where a number is unavoidable (`mobile_spec.rb`'s font size), compare with `be_within`, not `eq`.
  - **Exact scales:** the one place an exact scale *is* pinned — the title slide's — only holds locally; on CI it is range-checked, because colour-emoji layout differs across Chrome builds.
  - **Timing:** a slide that has just appeared (a slide change, the overview) is fitted in the next frame by a `ResizeObserver`. Wait for its `[data-fitted]` (or the exact `style`) before measuring it.
- **A song slide's chords appear twice in the document.** Every sung sub-slide of a song ends on a preview of the next slide's first line (`p.next-line`), and its chords are copies of the next slide's — `button.chord`s like any other. They come *before* that slide's own chords in document order. A lookup by chord text across the whole deck (`document.querySelectorAll('.reveal code.x')`) must skip `.closest('.next-line')`, or it lands on the slide before; `go_to_intro` in `chord_tooltips_spec.rb` does this. Within one slide, `first("#id code.d")` gets the lyrics' chord (the preview is the slide's last child); to get the preview's, scope to `#id .next-line`. Tab order passes through the preview's chords too.
- **The next-line preview starts out transparent.** It fades in only 3–6 s after its slide is shown, and Cuprite treats `opacity: 0` as invisible. A Capybara finder or matcher would wait for the fade, or fail with no match. Call `finish_next_line_fade` (`spec/spec_helper.rb`) right after reaching the slide, as if the reader had waited. Reading it with `evaluate_script` or `visible: :all` doesn't need this.
- **A chord is a `<button class="chord">` around its `<code class="a">`.** The `chord-active` marker, focus and `aria-expanded` sit on the button (`button.chord-active > code.f`); the colour class and the focus/hover ring sit on the `<code>` inside (read the ring from `document.activeElement.querySelector('code')`). Clicking the `<code>` works: the click bubbles to the button.
- **A real reload is `page.refresh`, not `visit` on the same URL.** Visiting the same `#/…` only jumps within the loaded deck; it never re-runs page load. Use `page.refresh` (see the presenter-reload examples in `index_html_spec.rb`).
- **Ports.** `spec/support/file_server.rb` serves the project on `127.0.0.1` on an **OS-picked free port**, so a second checkout's run doesn't collide. `spec/support/multiplex_server.rb` is **fixed on `127.0.0.1:18889` and refuses to start if that port is taken** — so the specs never quietly broadcast into a multiplex server left over from a manual test. Run manual multiplex tests on a different port.
- **Multiplex needs a session first.** A device in no session opens no socket at all. A live-sync example logs one tab in as host (`log_in_as_host`, which opens a session), reads its secret from the device's storage (`session_secret`) and opens the others with `join_session(secret)` — the `?live=` address a scanned QR code would open, which the page stores and strips from the address at once — *before* the host starts live scrolling — a tab that joins later only ever hears heartbeats, so it gets no invite or announcement. A tab that only needs to be in some session (the QR examples) can join a made-up one: `join_session('spec-qr')`. The spy and phantom sockets read `window.MULTIPLEX.secret`/`socketId`, which exist only once the tab has joined, so install them after that. Each `using_session` is a browser of its own, so its storage — and with it its session — is its own too; to stand for a new tab on the *same* device (or the home screen's app restarted), clear `sessionStorage` and visit the plain address, as the self-scroll example does for its presenter.
- **A toast moves the bottom corners.** When `#multiplex-toast` appears, 📡 and ⚙️ slide up clear of it over 0.3 s (`night.css`), and a click computed at the start of that slide lands where the button used to be — the dialog just doesn't open. `open_live_scroll_dialog` waits for the corner's transitions to finish before it clicks; do the same before clicking any bottom-corner button right after something that shows a toast.
- **`:focus-visible` flips on `focusin`, not on the first keydown.** Chrome enables `:focus-visible` as soon as any key is pressed, so the page reads the ring's visibility on `focusin`; a mouse click leaves a focus with no ring. A spec asserting the ring must account for this (focus by keyboard to see it, by click not to).
- **Not every media feature can be emulated.** CDP `Emulation.setEmulatedMedia` does **not** support `hover`, so a tooltip gated on `matchMedia('(hover: hover)')` can't be forced that way on the Linux runner. Simulate the pointer instead by patching `matchMedia` before the page's own scripts capture it, via `Page.addScriptToEvaluateOnNewDocument` — see the QR-modal example. Patching `matchMedia` does nothing for a CSS `@media` rule, though. For a touch screen, `Emulation.setTouchEmulationEnabled` makes Chrome report `(pointer: coarse)` to CSS as well; see the chevron example in `mobile_spec.rb`. That's also why CSS that should apply on a desktop gates on "not `pointer: coarse`" rather than on `hover: hover`.
- **`all(…)` that is expected to come back empty waits the full 10 s.** Capybara's `all` waits up to `default_max_wait_time` (10 s here) for a first match before it returns an empty list, so `expect(all(…)).to be_empty` passes, but only after ten seconds. Assert absence with `have_no_css(…)` instead, which returns as soon as nothing matches. That holds for a list helper built on `all`, too: `toc_filter_spec.rb` checks "no entries left" with `have_no_css(VISIBLE_ENTRY)`, not `visible_entries` being empty. Until 2026-10-29 two examples paid the ten seconds each, 20 of the suite's then 68 s.
- **`wait_for_js` never fails on its own.** It polls until the condition holds or two seconds pass, then returns quietly either way. Always follow it with an `expect` on the state it waited for. Otherwise the example stays green when the condition never held — a check once "passed" a scroll of the TOC that the fixture's short list couldn't even do, until it asserted `scrollTop` explicitly.

## Before you commit

The specs are timing-sensitive; one green run proves little. Run the changed file a handful of times and expect all green — a 1-in-5 flake is a real defect, not noise. Then run the whole suite (`bundle exec rspec`): it rebuilds the fixtures and the golden snapshots too, so a markup change surfaces there.
