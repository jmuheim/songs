This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Record decisions in [`decisions/`](decisions/), one file per entry** — see [DECISIONS.md](DECISIONS.md) for the format, and use the `songs-log-decision` skill to add one. Never append to a shared list.

## What this project is

A guitar song book generator. Songs are written in Markdown with inline chord notation. A Ruby script compiles them into an interactive Reveal.js HTML slideshow (`index.html`) and a print-friendly version (`print.html`).

## Working agreements

These are not descriptions of how things happen to work — they are commitments to keep. Follow them without being asked.

- **Commit straight to `master`; no pull requests.** This is a small, private project, and a branch-and-PR round trip costs more than it catches. New work goes onto `master` with no question about the branch, but it is committed only once the user has looked at it: show what changed, take their corrections, and commit after their OK. When the main checkout is busy (another session, uncommitted work), work in a separate git worktree on a short-lived local branch there (git won't check out `master` in two worktrees at once), then rebase it onto `master` and fast-forward `master` to it. A fresh worktree lacks what is gitignored: install the relay's dependencies (`npm ci --prefix multiplex-server`) before running the specs. Keep unrelated changes in separate commits. See [decisions/2026-10-28-commit-straight-to-master-no-pull-requests.md](decisions/2026-10-28-commit-straight-to-master-no-pull-requests.md) and [decisions/2026-10-29-commit-after-review-push-only-when-asked.md](decisions/2026-10-29-commit-after-review-push-only-when-asked.md).
- **Behaviour changes come with tests.** If you change the build pipeline, the chord regex, the multiplex logic, or anything in `style/*.js`, add or update the spec that pins that behaviour before considering the change done — and run `bundle exec rspec`. New behaviour with no covering spec is unfinished work. For the browser specs, follow the `songs-browser-specs` skill.
- **Keep the golden fixtures in sync.** `all-songs.md`, `index.html`, `print.html` and the fixtures under `spec/fixtures/` (except `golden/`) are build outputs — they are generated, not committed (gitignored; the specs regenerate the fixture HTML themselves). The one committed reference is `spec/fixtures/golden/`: when you change the markup or the generator, regenerate it with `bundle exec rake golden:update` in the same change — the golden specs exist to catch exactly the drift you'd otherwise leave behind.
- **One source of truth.** Don't copy logic that already lives in `lib/build_helpers.rb` (or anywhere else) into a second place. If the build and a spec both need a transformation, both call the same helper, so the spec tests what ships.
- **Skills are living artefacts.** The skills in `.claude/skills/` (`tab-to-song`, `songs-browser-specs`, `songs-log-decision`) describe real, current behaviour of this repo. When the song format, the build, or a workflow they document changes, update the matching skill in the same change. If a task reveals a repeatable workflow the skills don't yet cover, propose one.
- **Docs track reality.** This file and `README.md` must match what the code actually does. If you change a command, a dependency, or a default, update both.
- **Knowledge lives in the repo, not in a private store.** Record decisions, conventions, gotchas and working practices here, in [`decisions/`](decisions/), or in `README.md` — never in Claude Code's per-project memory. Repo files travel with the code, are reviewable, and are visible to everyone; a private memory is none of those. If something is worth remembering, commit it.
- **Push `master` only when asked, and only after a green local run; then watch CI.** A push deploys, so whether a commit goes live is the user's call, separate from their OK to commit it. After a commit, say how many commits `master` is ahead of `origin/master`. `bundle exec rspec` passes before every push. The push itself starts CI, which deploys to songs.josh.ch once its own run is green (`needs: rspec`, see [Deploy](#deploy)). A red run deploys nothing, so the site stays on the last green build. Watch it with `gh run watch <id> --exit-status`, and if it goes red, fix forward on `master` straight away. `master` has no branch protection and no required checks; this discipline is the gate.

## Build command

```bash
./build           # Build index.html, sw.js and print.html
./build --deploy  # HTML + deploy to songs.josh.ch
./build --dev     # Without the service worker (what ./dev builds)
./dev             # Watch, rebuild, and live-reload on every change (local only, no deploy)
```

Dependencies: Ruby 3.x, Pandoc (`brew install pandoc`), fswatch (`brew install fswatch`), browser-sync (`npm install -g browser-sync`).

Deploys to songs.josh.ch happen from CI on every push to `master` once the suite is green (see [Deploy](#deploy)); `./build --deploy` remains the manual fallback.

> **Dev gotcha:** `./dev` builds with `--dev`, without the [service worker](#offline-the-service-worker): with one, browser-sync's reloads would show what it keeps, not the build. Its page unregisters any left from an earlier `./build` served on the same address.

> **Dev gotcha:** `./dev` passes `--no-ghost-mode` to browser-sync. Ghost mode (on by default) syncs clicks across all open tabs and interferes with the multiplex feature — it makes button presses appear to fire on all "clients" simultaneously during local testing.

## Deploy

Deploying is a CI job (`deploy` in `.github/workflows/test.yml`), not something a local save does. It runs **only on a push to `master`**, and only **after the `rspec` job is green** (`needs: rspec`) — so an untested commit never reaches songs.josh.ch. Its own `concurrency` group serialises deploys. The job runs `./build` and `rsync`s `index.html` + `sw.js` + `style/` + `.htaccess` to the server (not `print.html`, matching the old manual deploy).

The server is reached with a dedicated ed25519 **deploy key** (secret `DEPLOY_SSH_KEY`), separate from anyone's personal key and locked on the server via `authorized_keys` to `rrsync` into `…/songs.josh.ch/` only — so the rsync target is relative. The host key is pinned in the workflow (no `StrictHostKeyChecking=no`); refresh it with `ssh-keyscan greip.uberspace.de` if the server ever rotates its key.

`./build --deploy` stays as the manual fallback: it rsyncs the same files from your machine using your own SSH access (absolute path), bypassing CI.

### Cache headers

The repo's root [`.htaccess`](.htaccess) ships with every deploy and tells Uberspace's Apache (`mod_headers`) to send `Cache-Control: no-cache, must-revalidate` for `.html`/`.css`/`.js`, and a year-long `immutable` cache for fonts. Without it, browsers fall back to heuristic caching of `index.html` and `style/*.css|js` — since those keep the same filename on every deploy, a cached copy never looks stale on its own, and phones with the song book added to the home screen (an even more aggressive webview cache) could sit on a build from weeks ago. `no-cache` still lets the browser keep a local copy; it just forces a conditional request every time, so an unchanged file comes back as a cheap 304. Once the [service worker](#offline-the-service-worker) is in control, a load asks nothing at all: it serves the page from its own cache, and the browser checks only `sw.js` (a `.js`, so `no-cache` too, and a service worker's script skips the HTTP cache anyway) to find a new build.

## Song file format

Each song lives in `content/songs/<slug>.md`, where `<slug>` is its H1 lowercased, with `.`/`,`/`'` dropped, German umlauts transliterated (`ä`→`ae`, `ö`→`oe`, `ü`→`ue`, `ß`→`ss`), and the remaining spaces turned into underscores (everything else — `&`, `!` — passes through as-is): `# Family Portrait - P!nk` lives in `family_portrait_-_p!nk.md`, `# Knockin' on Heaven's Door - Bob Dylan` in `knockin_on_heavens_door_-_bob_dylan.md`, `# Über den Wolken - Reinhard Mey` in `ueber_den_wolken_-_reinhard_mey.md`. The H1 itself keeps its real spelling (punctuation and umlauts both) — only the filename is transliterated/stripped, to stay plain-ASCII-friendly in a shell. Structure:

```markdown
# Song Title - Artist Name

## Infos über das Lied

- Sprache: Englisch
- Genre: Mantra
- Gastgeber: Josua, Monika
- [Lied auf YouTube](https://youtube.com/...)
- [Tab-Quelle](https://...)

## Spielhinweise

```
       |E A D G B e|
       |-----------|
A7sus4 |x 0 2 0 3 0|
```

## Section Name

Lyrics with [Chord] inline like this [Am] and here [G7].
```

- **H1** = `Title - Artist` (the literal separator is a space, a hyphen and a space — reserved, so a title may not itself contain that exact substring; `74-75`'s unspaced hyphen is fine). Drop the artist entirely — just `Title`, no trailing `- …` — when there's no specific one to credit: a traditional/folk song, written `Traditional` for an English title or `Traditionell` for a German one (the two forms this book already uses; any flag or other annotation that used to ride along in the parenthetical, e.g. `(Traditionell 🇨🇭)`, is dropped with it rather than kept on the bare title). One per file, shown as the slide title. **Nothing but blank lines may follow it before the first H2** — `validate_song!` aborts the build otherwise; a capo note or any other aside belongs in `## Infos über das Lied` instead (e.g. `- Capo: 3. Bund`).
- On a song's own title slide, `split_song_artist` (`lib/build_helpers.rb`, part of the shared pipeline below) splits that H1 back apart: the title stays in the `<h1>`, the artist becomes a sibling `<p class="song-artist">` right after it, styled smaller and a shade dimmer than the title (`style/shared.css` for size; for colour, `style/night.css` mixes the title's with a little of the background, see [Colours](#colours), and `style/serif.css` has its own for print). A bare `Title`-only H1 (no artist) is left as a plain `<h1>`, same as the Einleitung. This only touches each song's own `section.level1 h1` — never the deck's own title-slide cover (`section.deck-title-slide`).
- **H2** = section (each becomes a sub-slide)
- **Chords** use `[ChordName]` inline in lyrics
- An **`## Infos über das Lied`** section at the top holds the song's tags and its resource links together, authored in this shape directly (not assembled at build time): one `- Sprache: <value>` line, one `- Genre: <value>[, <value>...]` line (free text — keep the vocabulary consistent: Sprache `Deutsch` / `Englisch` / `Mundart` / …, Genre `Pop` / `Rock` / `Schlager` / `Country` / `Traditionell` / `Mantra` / `Kids`; a song in more than one genre names them comma-separated, e.g. `Traditionell, Kids`), and an optional `- Gastgeber: <value>[, <value>...]` line naming whoever hosts the evening the song is earmarked for (free text, e.g. `Josua`, or `Josua, Monika` for more than one — comma-separated on the one line, like Genre), followed by the resource links (YouTube, tabs, tutorials) as plain Markdown link bullets, plus any other aside (e.g. `- Capo: 3. Bund`) that would otherwise float between the H1 and the first H2. The YouTube link is always labelled `[Lied auf YouTube]`; other links are free text, in German like the rest of the slide (`Tab-Quelle`, `Gitarren-Tutorial`, …). `song_tags` in `lib/build_helpers.rb` parses the `Sprache:`/`Genre:`/`Gastgeber:` lines into `[category, value]` pairs, splitting a comma-separated Genre or Gastgeber line into one pair per value (other list items — a Capo note, the resource links — are not tags and are skipped); the category is exactly what was written, not inferred from a fixed vocabulary, so a language, genre or host this book hasn't seen before still lands in the right [table-of-contents tag filter](#table-of-contents-tag-filter) control. `validate_song!` **requires** at least one Sprache and one Genre tag, aborting the build otherwise — tagging is not optional; Gastgeber is not required the same way, since not every song needs a host attached.
- An optional **`## Spielhinweise`** section, right after `## Infos über das Lied`, holds alternate chord fingerings (e.g. a capo shape or a barré alternative) as a plain code block, same as the [chord tooltip](#keyboard-and-dialogs)'s guitar tab.
- `merge_about_section` in `lib/build_helpers.rb` splices `## Spielhinweise` (`NOTES_HEADING`) into `## Infos über das Lied` at build time — the source file keeps them as two sections (above) for readability; nothing else on disk needs to change when editing a song. This merged section is stripped from `print.html` entirely (tags, resource links and alternate fingerings are all screen-only features) — see [`spec/fixtures/golden/infos_ueber_das_lied.html`](spec/fixtures/golden/infos_ueber_das_lied.html).
- `content/Introduction.md`, the Einleitung, is always prepended as the first slide
- **The song book's own words are German, playing directions are not.** Section headings are German (`Strophe 1`, `Refrain`, `Vor-Refrain`, `Zwischenspiel`, `Überleitung`, `Mittelteil`; `Intro`, `Outro`, `Bridge`, `Solo`, `Instrumental` are the same in both), and so are the resource links' labels. Directions in the lyrics (`_(Repeat and fade)_`, `_(x2)_`, `Barre chords`) and the notes in `## Spielhinweise` stay as the tab wrote them, mostly English: musicians who don't speak German play along too. Chord names stay international: `B`, not `H`. See [decisions/2026-11-02-the-song-book-speaks-german-its-playing-directions-dont.md](decisions/2026-11-02-the-song-book-speaks-german-its-playing-directions-dont.md).

## Chord rendering pipeline

The Ruby script transforms `[Chord]` markers before passing to Pandoc:

```
[C] → `C`{.c}    (CSS class = lowercase first letter)
[Am] → `Am`{.a}
[G7] → `G7`{.g}
```

Pandoc renders these as `<code class="a">Am</code>` etc. CSS in `style/shared.css` assigns a distinct color per chord letter (A=red, B=gray, C=blue, D=green, E=yellow, F=violet, G=brown). In `index.html` (not `print.html`), `chord_buttons` (`lib/build_helpers.rb`, in `post_process_index`) then wraps each one in a real button — `<button type="button" class="chord"><code class="a">Am</code></button>` — see [Keyboard and dialogs](#keyboard-and-dialogs). Only classes `a`–`g` and `x` are wrapped, the ones `chords.js` has a fingering for.

The regex only matches `[Word]` not followed by `(` — so standard Markdown links `[text](url)` are left untouched.

## Shared pipeline

`build` and `spec/support/fixture_builder.rb` run the same code, in `lib/build_helpers.rb`: `songbook_markdown` (front matter with `lang: de-CH`, the introduction, the songs with their chords marked up), `pandoc!`, `post_process_index` and `post_process_print` (both of which call `split_song_artist`, see [Song file format](#song-file-format)). What differs is a parameter — `assets:` (`style/` beside `index.html`, `/style/` for the fixtures served from `spec/fixtures/`), the multiplex config and `service_worker:` (`sw.js`, or `nil` for `./build --dev`). `service_worker` writes `sw.js` from the finished `index.html` for both. Change the pipeline there, not in one of its callers.

## Table of contents tag filter

The TOC can be filtered by Sprache (language), Genre and Gastgeber (host). Each song's tags live in its `## Infos über das Lied` section (see [Song file format](#song-file-format)); the build carries them into the TOC and `style/toc-filter.js` wires the interaction:

- `song_tags` parses the `Sprache:`/`Genre:`/`Gastgeber:` list items of each song's `## Infos über das Lied` section into `[category, value]` pairs. `build` and `fixture_builder` collect one such array per song — in the same order the TOC lists them — and pass it to `post_process_index` as `tags:`.
- `inject_toc_filter` (a Nokogiri pass, like `wrap_slide_content`) first turns Pandoc's TOC `<ul>` into an `<ol>` (shown without numbers: `list-style: none` in `shared.css`, which also drops the margin and padding they sat in, so the list is centred) and drops its first `<li>` — the Introduction, which isn't a song and carries no tags — entirely, rather than merely excluding it from the filter; the remaining `<li>`s then line up with `tags[i]` **by order**, not by re-deriving Pandoc's slugs. It adds `data-sprache="Englisch"` / `data-genre="Pop"` / `data-gastgeber="Josua,Monika"` attributes to each one and prepends a `<fieldset id="toc-filter">` (a `.visually-hidden` legend „Filter" — the Sprache/Genre labels next to the selects and the „Lieder von" button already say what's being filtered on-screen, so the outer legend only needs to reach a screen reader) holding one `<select>` each for Sprache/Genre (single-choice; `toc_filter_select`, sorted, first option „Alle") that has at least one tag, a „Lieder von: Alle" button for Gastgeber (`toc_filter_gastgeber_button`, if any song names one; its `.toc-filter-selection` span lists the checked hosts — „Alle" with every one checked, „Niemand" with none — and ends in „…" rather than widening the bar) and a „Zurücksetzen" button. The Gastgeber themselves are checkboxes in a `<dialog id="gastgeber-modal">` of their own (`toc_filter_gastgeber_dialog`: title „Lieder von", an info line, one checkbox per distinct host, sorted, and „OK"), appended to `<body>` — outside the slides, because reveal.js keeps every slide but the current one `inert` and the host's login opens it on any of them. Multi-choice rather than a select, since more than one host's songs are often worth seeing at once; a row of them in the bar did not fit its width, which is why they are a dialog — see [decisions/2026-10-31-gastgeber-get-a-dialog-of-their-own-songs-von.md](decisions/2026-10-31-gastgeber-get-a-dialog-of-their-own-songs-von.md) and [decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md](decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md). plus a `<p id="toc-filter-empty" class="toc-hidden">Keine Ergebnisse, bitte Filter anpassen</p>` after the list for `toc-filter.js` to reveal when a filter leaves nothing standing. With no tags anywhere, neither the fieldset nor that message is added (only the `<ol>`/Introduction-removal step still runs).
- `style/toc-filter.js` re-renders on every `change` and hides the `<li>`s that don't match (`.toc-hidden`, also toggled on `#toc-filter-empty` but inverted — shown only once nothing else is). Sprache and Genre combine with **AND** (a song must match the selected Sprache *and* the selected Genre, for whichever of the two has a selection); Gastgeber's checkboxes **start out all checked**; with all of them checked there is no filter (so a song without a Gastgeber stays), with some unchecked a song matches if it names *any* checked host (**OR**; one without a Gastgeber hides), with none checked nothing matches (the „Keine Ergebnisse" message) — then **AND** into the rest — see [decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md](decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md). „Zurücksetzen" clears every control (checks every Gastgeber again); untagged entries hide while any filter is active. The selects, the buttons and the dialog's checkboxes are real form controls, so the `keyboardCondition` in `body-controls.html` already keeps their keys (Space, arrows, Home/End — reveal.js's own guard only excludes input/textarea, not select/checkbox) from reaching Reveal. Outside a session the selection is local to each client and is **not** synced over multiplex. **In a session the filter is the host's, for everyone:** the Gastgeber checkboxes say whose songs the evening has (the dialog stays „Lieder von" — outside a session one browses the book as a plain visitor and may not know what a Gastgeber or a session is, so it never says „Anwesend"), and a Sprache or Genre the host picks holds for every list in the session too (see [Multiplex](#multiplex-live-sync)). A Sprache or Genre the host leaves at „Alle" is each guest's own to pick. `tocFilter.setSession({ present, sprache, genre }, editable)` switches them over: set as the host chose and disabled for everyone but the host — the checkboxes always, a select once the host has picked a value in it, „Zurücksetzen" once neither select is the guest's (greyed out in `night.css`) — with an info line in the dialog saying who chooses. A guest's own pick in a free select is left as it is by every later `setSession` (one for a changed `present` included); it goes back to „Alle" only when the host lets go of a value it had picked there, and the guest's „Zurücksetzen" clears the free selects only. `null` gives them back as a filter of one's own, nothing filtered (every Gastgeber checked, Sprache and Genre „Alle"). `tocFilter.onSessionChange(fn)` hands the host's own changes, `{ present, sprache, genre }`, to `body-controls.html`. `tocFilter.allHosts()` lists every Gastgeber: what a session's `present` starts as. `tocFilter.openDialog()` opens the dialog (`false` where no song names a Gastgeber). The dialog keeps its keys from Reveal and closes on its backdrop, like the others. The host's „Zurücksetzen" clears Sprache and Genre for everyone and leaves the Gastgeber alone in a session: who is here is no filter. See [decisions/2026-11-11-the-host-filters-the-table-of-contents-for-the-whole-session.md](decisions/2026-11-11-the-host-filters-the-table-of-contents-for-the-whole-session.md).
- Styling: fieldset/select/checkbox/button layout, the `<ol>`'s constant ~90% width and its `<li>` title truncation (`overflow: hidden; text-overflow: clip`, so a title wider than that box is cut instead of wrapping or stretching the box, and fades out at the row's end rather than ending in „…": a `::after` overlay on the `<li>` in the list's own background (`--r-background-color`, whatever the [colours](#colours)) with a transparent left edge, its colours in `night.css` — an overlay, not a mask on the link, which would cut off the link's focus ring; in a session the row's ❤️ does the fading and the overlay is off, see [Wishes](#multiplex-live-sync)) all live in `shared.css`; colours and the sticky bar in `night.css`. The bar is `position: sticky; top: 0`. Reveal's `display: 'flex'` config (`post_process_index`) makes every present slide, `#TOC` included, a flex container — flex's default `align-items: stretch` would otherwise cap `.slide-content` at `#TOC`'s own (viewport) height instead of its full, much taller, content height, and a sticky element only sticks within its containing block, so past that cap the filter bar would just scroll away with everything else instead of staying put. `section#TOC > .slide-content { align-self: flex-start }` (`night.css`) is what actually keeps it visible while the list scrolls underneath it — see [decisions/2026-10-04-toc-filter-sticky-broke-past-one-screen-of-flex-stretch.md](decisions/2026-10-04-toc-filter-sticky-broke-past-one-screen-of-flex-stretch.md).

Each song's row also ends in a ❤️ (`button.song-wish`, added in the same per-`<li>` pass from the entry's own `#/<slug>` link), shown only in a session — see [Wishes](#multiplex-live-sync) under Multiplex.

The golden `spec/fixtures/golden/toc.html` pins the generated markup; `spec/unit/song_tags_spec.rb` covers the parser, `spec/integration/golden_html_spec.rb` the injected markup and the print stripping, and `spec/browser/toc_filter_spec.rb` the interaction (including a real past-one-screen scroll, which is what actually exercises the sticky fix above).

## Output files

These are **generated, not committed** (gitignored; `./build` writes them, CI rebuilds them for the deploy, and the specs rebuild the fixture copies):

- `all-songs.md` — intermediate concatenated Markdown
- `index.html` — interactive night-themed Reveal.js presentation
- `sw.js` — the service worker, `lib/service-worker.js` with the build's version and files (see [Offline](#offline-the-service-worker)); not written by `./build --dev`
- `print.html` — serif-themed version for printing. Open it as `print.html?print-pdf` in Chrome and print: reveal.js then lays out every slide as a page of its own

## Tests

```bash
npm install --prefix multiplex-server   # once; needs Node.js >= 18
bundle exec rspec
```

`spec/support/fixture_builder.rb` builds `spec/fixtures/index.html` and `print.html` from the songs in `spec/fixtures/songs/` at the start of the run (they are gitignored, not committed). The browser specs serve them with WEBrick on `127.0.0.1` and a port the OS picks (`spec/support/file_server.rb`), so a second checkout's run does not collide with it. Opening, joining and leaving a session (`log_in_as_host`, `session_secret`, `join_session`, `open_live_scroll_dialog`) is `spec/support/session_helpers.rb`, shared by every browser spec that needs one.

**The specs never touch the live multiplex channel.** `spec/support/multiplex_server.rb` runs `multiplex-server/` — the official reveal-multiplex package, the same software the public Railway server runs, pinned by commit — on `127.0.0.1` (`localhost.js` keeps it off the LAN) for the whole run. The fixture points at it by URL; the sessions the specs open get their secrets from the page itself, as on the live site, and the other tabs join them by the host's address (`join_session`). Before, the fixture carried `multiplex-token.json`, so the „live sync" spec became master on the channel songs.josh.ch listens to, and moved anyone who had it open at the time. It listens on a port the OS picks (`PORT=0`; `localhost.js` writes the one it got to `PORT_FILE`), like the file server: two runs at once in two checkouts (two sessions, each in its worktree) used to collide on the fixed 18889, and the second one's specs failed. The fixture carries the server's URL, and is built before any spec starts the server, so asking for the URL (`MultiplexServer.url`) starts it. A multiplex server from a manual test can't be mistaken for the specs' own any more either: it sits on another port. See [decisions/2026-11-12-the-specs-multiplex-server-takes-any-free-port.md](decisions/2026-11-12-the-specs-multiplex-server-takes-any-free-port.md).

Nothing leaves the machine during a run: the fonts are local too (see below). The slide-zoom expectations are exact values measured with those fonts, so they also catch a font that renders differently. The one exception is the title slide, whose emoji Chrome lays out differently across its own builds: its exact scale holds locally but is only range-checked on CI (see [emoji zoom is not reproducible across Chrome builds](decisions/2026-09-30-emoji-zoom-is-not-reproducible-across-chrome-builds.md)).

`bundle exec rake golden:update` regenerates the golden snapshots in `spec/fixtures/golden/` after an intended markup change.

**CI runs the whole suite on every pull request, and on every push to `master`** (`.github/workflows/test.yml`): Ruby 3.2, Pandoc pinned to the same 3.9.0.2 the golden fixtures were built with, the `multiplex-server/` dependencies via `npm ci`, then `bundle exec rspec`. `push` is deliberately scoped to `master` only — left unscoped, a branch with an open PR would run the identical suite twice on every commit (`push` and `pull_request` both fire); `master` still needs its own `push` trigger since the deploy job's `needs: rspec` depends on an `rspec` run from that same push-triggered workflow (merging a PR doesn't re-fire `pull_request`). `Gemfile.lock` carries `x86_64-linux` alongside `arm64-darwin` so the Linux runner resolves nokogiri's native gem — regenerate both platforms with `bundle lock --add-platform x86_64-linux` if you ever relock.

**Cold-boot retry:** headless Chrome cold-starts on the first browser example of a run, and on a loaded runner that launch handshake used to occasionally exceed `process_timeout` and fail the whole run (and the deploy) with `Ferrum::ProcessTimeoutError: Browser did not produce websocket url …` — not a real assertion, just a flaky launch. A `prepend_before(:each, type: :feature)` hook in `spec/spec_helper.rb` now forces the browser up and, on a boot timeout, quits the dead process and retries the launch (up to three attempts), so a flaky cold start no longer reddens the run. If a `ProcessTimeoutError` still surfaces, the launch failed three times running — treat that as a real environment problem (missing browser, starved runner), not a re-run.

## Vendored reveal.js

`style/revealjs/` holds reveal.js **6.0.2** — only the five files the pages load (`dist/reveal.js`, `reveal.css`, `reset.css`, `theme/night.css`, `theme/serif.css`) plus its `LICENSE`. Everything under `style/` is deployed, so the rest of the release (tests, demo, other themes, `package-lock.json`) stays out. The paths match Pandoc's `revealjs-url`, which is why the `dist/` folder is kept.

To upgrade, copy those five files from `dist/` at the release's tag in the Git repository (`https://raw.githubusercontent.com/hakimel/reveal.js/<tag>/dist/…`), remove the two Google Fonts `@import`s from the start of `theme/night.css` again, rebuild and run the specs. Pandoc's template also loads the notes, search and zoom plugins from their reveal.js 5 paths; the song book uses none of them, and `build` removes those script tags.

6.0.2 is the minimum: it makes every slide but the current one `inert` ([hakimel/reveal.js#1587](https://github.com/hakimel/reveal.js/issues/1587)). With 6.0.1, `Tab` on the Introduction reached the table of contents' links, which reveal.js keeps rendered next door but invisible — 35 of 40 presses landed there.

**Fonts:** `style/fonts/` holds Montserrat 700 and Open Sans (400/700, with italics), the theme's own, and the other fonts ⚙️ offers, every one for the titles and for the text (see [Keyboard and dialogs](#keyboard-and-dialogs)): Playfair Display, Oswald and Dancing Script (700); Pacifico, Permanent Marker, Antic Slab, VT323, Londrina Outline and Nabla (400); Atkinson Hyperlegible, Lora, Nunito (400/700, with italics), Caveat, Comic Relief — an open stand-in for Comic Sans, which Microsoft's license keeps out of the book — and Lexend (400/700). All as Google Fonts serves them, every subset, with their licenses (OFL; Permanent Marker's is Apache 2.0), and `fonts.css` with Google's `@font-face` rules pointing at them. Nabla is a colour font in two builds, COLRv1 as Google serves it to Chrome and OpenType-SVG as it serves it to Safari (which draws COLRv1 without its colours; `-safari.woff2`), picked by `tech(color-COLRv1)` in its rules. OpenDyslexic (400/700, with italics) is not on Google Fonts: its project's own woff2 files, unchanged (OFL, its name reserved, so it must not be modified). „Liedli Symbole" and „Liedli Hieroglyphen" are built here, by `lib/build-liedli-fonts.py`, from Noto Sans Symbols 2 and Noto Sans Egyptian Hieroglyphs (OFL, no reserved name): each letter, umlaut and digit mapped to a picture, Wingdings-like, the rest dropped; Wingdings itself may not be shipped, and the open fonts map their pictures to Unicode's own code points, not to letters. 111 woff2 files in all. `post_process_index` links it; the night theme's own `@import`s from fonts.googleapis.com are removed, so no visitor's browser asks Google for anything. A browser downloads a font only once a page uses it, and only the subsets its text needs, so the fonts nobody picks cost nothing. To offer another one: fetch `https://fonts.googleapis.com/css2?family=…` with a current Chrome's user agent (or Google serves no woff2), download every `src` it names into `style/fonts/`, append its rules to `fonts.css` with `src` pointing at the local files, add its license from [google/fonts](https://github.com/google/fonts) (`ofl/<family>/OFL.txt`), a `body[data-title-font]`/`[data-text-font]` rule in `night.css` and a radio button with its sample `<img>` in `body-controls.html`, then run `bundle exec rake fonts:samples` for the picture. The theme spec loads every font on offer and fails on a family that doesn't.

`style/qrcodejs/` holds qrcodejs 1.0.0 (the 🔗 dialog's QR code) with its `LICENSE`, served from the song book itself rather than jsDelivr.

`style/socketio/` holds socket.io's client 2.5.0 (`dist/socket.io.js`, with its `LICENSE`), the very file the relay serves at `/socket.io/socket.io.js`, byte for byte. It used to be loaded from there, on every page load: another host to reach (`max-age=0`, so a request every time), and a synchronous script, so on a slow connection the chords, the TOC filter and the ❤️ waited for it, and with the relay out of reach 🔥 stayed dead until a reload (its handlers only start with `window.io`). Served from `style/`, it comes and goes with the page, and a device in no session never contacts the relay at all. To upgrade, copy `node_modules/socket.io-client/dist/socket.io.js` from `multiplex-server/` (pinned by commit, the same server Railway runs) once `npm ci` has fetched it, so the client always matches the server's major version.

## Slide layout and fit

Reveal's own `center: true` only centers a slide **among its siblings inside a `.stack`** (`section.stack { flex-direction: column; justify-content: center }` in `shared.css`) — a song or the Introduction, which have sub-slides, gets this for free. `section.deck-title-slide` has no sub-slides, so Pandoc never wraps it in a `.stack`, and it needs its own rule (`shared.css`) to center vertically. That rule uses `align-items: center`, not the flex default `stretch`: `style/slide-zoom.js` measures `.slide-content`'s natural (shrink-to-fit) width to decide how far it can scale up, and a stretched-to-100%-width box always measures as already full, capping the scale at 1 instead of the ~1.4 the title actually fits.

**Every rendered slide is fitted, whenever its size could change.** `slide-zoom.js` scales each slide's `.slide-content` (on the title slide, the Introduction and every song slide, i.e. all but the TOC) with `transform: scale()`, by its natural size against the room on screen. A `ResizeObserver` watches every one of them, the deck (`.reveal`, i.e. the window) and the right chevron. A slide's own entry re-fits that slide, and the deck's or the chevron's re-fits them all. The deck, not `<html>`: the two are the same box except during [Vollbild](#vollbild) on an iPhone, where `<html>` is many screens tall and doesn't change as Safari's bars come and go. Observer callbacks run after layout and before paint, so a slide is fitted in the very frame it appears, whether Reveal shows it next to the current one, the overview shows dozens at once, the fonts arrive, or „Akkorde anzeigen" changes its line widths. There's no list of events to keep up to date.
- **Why a transform, not CSS `zoom`:** a transform leaves the layout alone, so the observer sees the natural size and the scaling never sets it off again. `zoom` re-wrapped the text at another width than was measured.
- **No unfitted frames:** until its first fit, a slide's content is `visibility: hidden` (`night.css`, with a 1s animation that shows it anyway should the script never run). A reload shows a blank slide for a moment, never one at the wrong size. `post_process_index` loads `slide-zoom.js` before every other script.
- **Title slides by their widest line:** a title slide (the deck's own, the Introduction's, every song's — `TITLES` in `slide-zoom.js`) holds nothing but lines of text, and is measured by the widest of them (a `Range` over each child's contents), not by its box. A title too long for one line wraps, and its box then takes the whole width while its lines fall short of it: measured by the box, a song's title on an iPad in portrait stayed at scale 1, a third short of the edges. Lyric slides need none of this: they are `white-space: nowrap`, so their box is their widest line. See [a wrapped title is fitted by its widest line](decisions/2026-10-28-a-wrapped-title-is-fitted-by-its-widest-line.md).
- **A title takes as many lines as make it largest:** on one line, a long title fills the width of a wide screen and leaves most of the height empty (three quarters of it on an iPad in landscape). `wrapTitles` (`slide-zoom.js`) measures the heading's words once on a single line, works out the narrowest split into 1, 2, 3, … lines from where they stand, predicts each one's scale against the room, and sets the winner as the heading's `max-width` (`shared.css` centres the heading and balances its lines with `text-wrap: balance`). The best count depends on the title *and* the screen's shape: „Imagine (John Lennon)" takes three lines on a 1280×800 desktop, two on a phone held sideways, where a third would cost more height than it saves width. One line is always a candidate, so no title comes out smaller than unwrapped. Rewrapping changes the content's size after the observer reported it; it would report it again in the same frame and Chrome raises „ResizeObserver loop completed with undelivered notifications", so a rewrapped content is unobserved and observed afresh from the next frame. Lyrics never wrap: a line of lyrics is a musical phrase, its chords placed within it. See [a title takes as many lines as make it largest](decisions/2026-10-28-a-title-takes-as-many-lines-as-make-it-largest.md).
- **Overview:** the overview gives every slide the full screen height (`.reveal.overview .slides section { height: 100% }`). The fitted contents are `align-self: center` (`night.css`) so they keep their natural height there instead of stretching to it, which capped every overview slide at 1.
- **Chevrons:** the room is the window minus a gutter on each side as deep as Reveal's chevrons reach in (see [Desktop navigation](#desktop-navigation-chevrons)). That's the side chevrons' depth on the left and right, and the up/down ones' at the top and bottom, measured from their layout offsets, not `getBoundingClientRect` (Reveal slides the chevrons in and out with a transform). Where the chevrons are hidden, they measure 0 and the content gets the whole screen.
- **Side effects:** `chords.js` multiplies a chord's computed font size by this scale (rendered box over layout box) to size its tooltip, since `getComputedStyle` leaves a transform out.

See [slides are fitted by a ResizeObserver, with transform: scale()](decisions/2026-10-28-slides-are-fitted-by-a-resizeobserver-with-transform-scale.md).

## Next-line preview

**Every sung sub-slide of a song ends on a preview of what comes next**, so whoever scrolls can read ahead and is never late: „Danach:", the next sub-slide's heading, „-" and its first line, chords included, then „..." („Danach: **Refrain** - I was the [Am] one who let you [C] know..."), or „Ende des Lieds" on the song's last sub-slide. `inject_next_line_previews` (`lib/build_helpers.rb`, in `post_process_index` before `wrap_slide_content`) appends a `<p class="next-line">` to each `section.level2` of every song but its „Infos über das Lied" slide. Neither that slide nor the song's own title slide gets one (nothing is sung there yet), nor does the Introduction (the first stack, skipped by order like in `inject_toc_filter`), nor `print.html`. The "first line" (`first_line`) is the next slide's first block after its heading, up to the first `<br>`; Pandoc's soft wraps become spaces.

- **Layout:** it sits inside `.slide-content`, below the lyrics, so `slide-zoom.js` fits it together with them. `shared.css` sets it at 0.6em under a rule. It never wraps, like the lyrics: a preview wider than the lyrics widens the slide, and the whole slide is fitted to it (a short Intro or Interlude gets smaller for it). It keeps the lyrics' colours, and its heading (bold) the slide titles' (`night.css`). It is dimmed by its opacity alone, which never gets past 60%. Only the separating rule has a colour of its own, mixed from the text and the background (`night.css`, see [Colours](#colours)).
- **It fades in late, and doesn't snap away.** It is only needed toward the end of a slide, so it stays out of the way at first. When its slide becomes the current one (Reveal's `.present`), the preview is fully transparent for 3 s, then fades in slowly to 60% over another 3 s. Every visit starts over. „Ende des Lieds" has nothing to read ahead and shows at 60% at once. Leaving, it keeps whatever opacity it had while Reveal moves and fades the whole slide out (0.8 s, `transitionSpeed: 'default'`), and is reset only after that. These are CSS transitions in `shared.css`, not an animation, which would end the instant `.present` goes. `@starting-style` makes a slide shown straight from `display: none` (a jump, the first load) start from transparent too. A chord in the preview that takes the focus (`:focus-within`) shows it at once, so the focus never sits on something invisible. Cuprite counts `opacity: 0` as invisible, so a spec that clicks or reads the preview first calls `finish_next_line_fade` (`spec/spec_helper.rb`).
- **It is ordinary content.** Screen readers read it too: while a song is live-scrolled, a follower cannot move on to read ahead (and reveal.js keeps the other slides `inert`). Its chords are chord buttons like any other (Tab stops, fingering on click); hiding the chords in ⚙️ hides these with the rest. `inject_next_line_previews` runs before `chord_buttons`, which wraps these copies along with the rest. `chords.js` sizes a preview chord's fingering as if the chord were set at the lyrics' size, not at the preview's 0.6em. A spec that looks up a chord by its text across the deck must mind these copies, which come *before* the next slide's own chords in the document.

The golden `spec/fixtures/golden/imagine_verse1.html` pins the markup, `spec/unit/next_line_preview_spec.rb` the extraction, `spec/browser/index_html_spec.rb` the single line (slide zoom) and the fade (next-line preview), and `spec/browser/chord_tooltips_spec.rb` its chords. See [decisions/2026-10-28-each-song-slide-previews-the-next-line.md](decisions/2026-10-28-each-song-slide-previews-the-next-line.md).

## Desktop navigation: chevrons

**Reveal's chevrons show on a desktop, at the screen edges.** Pandoc's `controls: true` is kept, and `post_process_index` switches `controlsLayout` to `'edges'`: ‹ › at the left/right middle, ˄ ˅ at the top/bottom centre, clear of the four corner buttons (the default bottom-right cluster sits exactly where 🚀 is). `night.css` hides them under `@media (pointer: coarse), (width < 500px)`: a touch screen swipes instead, and below 500px reveal.css drops the edges layout and falls back to that bottom-right cluster. It is not gated on `(hover: hover)`, because headless Chrome on the Linux CI runner reports no hover and would hide them on the "desktop" the specs test. While a song is live-scrolled, `applyNavMode` turns them off for the scroller and the followers, and back on once it ends.

**A trackpad swipe or the mouse wheel does not page the deck.** Reveal only handles swipes from a touch screen; a trackpad sends `wheel` events instead. Paging on those was built and then dropped: telling a swipe's momentum tail from the next swipe needs guesswork about the deltas (no web API exposes the trackpad's own phases), and it never felt reliable on a real MacBook. The chevrons and the arrow keys are the desktop's way through the book. See [desktop chevrons at the edges, no trackpad paging](decisions/2026-10-28-desktop-chevrons-at-the-edges-no-trackpad-paging.md).

Pandoc itself gives this slide `id="title-slide"` and nothing else; `rename_title_slide_id` (`lib/build_helpers.rb`, the first step of both `post_process_index` and `post_process_print`) swaps that for `class="deck-title-slide"` before anything else runs. reveal.js's Location plugin builds the URL hash from the current slide's id, so the id, left alone, pinned `#/title-slide` into the address bar forever after the slide was first shown — a plain `index.html` URL never came back. Every selector that targets this slide, in CSS or JS, must read `section.deck-title-slide` (the element type, not a bare class): reveal.js copies a slide's classes onto its `.slide-background` div too, and a bare `.deck-title-slide` would also catch that. See [decisions/2026-10-05-title-slide-id-replaced-with-a-class.md](decisions/2026-10-05-title-slide-id-replaced-with-a-class.md).

## Keyboard and dialogs

**The URL is written the moment the page is hidden** (`visibilitychange`): Reveal writes it at most once a second, and iOS stops that timer in the background, so a phone that switched apps right after a slide change and was discarded there reloaded a slide early.


**The controls sit in four corners, one in each.** Top left: 📖 jumps to the table of contents (hidden while live scrolling locks this device's navigation — see Multiplex below). It's a link to `#/1`, but a click goes by `Reveal.slide` (`gotoToc`) instead of following it: a navigation leaves an entry in the history, and on an iPhone in [Vollbild](#vollbild) Safari showed its bars again after one. Reveal's own paging writes the URL with `replaceState`, which Safari lets be. A click with a modifier key still opens the link, in a new tab, say. Top right: ↕️ toggles [Vollbild](#vollbild). Bottom left: 🔥 opens the live-scroll dialog, a badge on its corner saying this device's role at a glance; the dialog holds 🔑 (log in as host, or take the role over), and, depending on the role, 🚀 (start or end live scrolling), 🔗 (the session's QR code) and 🏁 (end the session); 🚀 and 🔗 used to be corner buttons of their own (see Multiplex below). Bottom right: ⚙️ opens the settings. Reveal's own chevrons sit at the screen edges between them, on a desktop only (see [Desktop navigation](#desktop-navigation-chevrons)). On a phone (`width < 500px`, or `height < 500px` for one held sideways) the dialogs take a smaller font and margins, or the live-scroll dialog ran off the bottom; held sideways, the settings dialog also puts the colours' label beside their select, and the colour pickers under it. Its font list scrolls, as tall as the screen leaves room for (`svh`, a phone's bars shown); on a larger screen it is set at 1.5rem, smaller than the other dialogs, or it ran past the bottom of a laptop's (`mobile_spec.rb` opens every dialog at 844×390, 375×667 and 1280×680, the background's with and without a picture, whose veil and parallax checkbox show only with one).

**They fade out while they aren't needed.** A few seconds after the page loads (5 s, the first time with their labels shown as if they were tooltips, `controls-intro`), the four buttons and a desktop's chevrons fade out over a second (`controls-idle` on `<body>`, `night.css`). A tap anywhere on the page (a pointer that comes up within 10 px of where it went down), a mouse that moves, or the keyboard's focus on one of them brings them back, to fade again 3 s later (`body-controls.html`). A swipe or a key that pages doesn't: they would be up on every slide. Nor does a tap that does something of its own (on a chord for its fingering, a link, a button, the TOC's filter: `ACTS`), or one that closes a chord's fingering again (`chords.js` closes it on any click): reading a chord should not bring them up, and on the TOC they would cover the filter bar's ends.
- **Faded, they take no taps** (`pointer-events: none`; the `.controls-group` wrappers never take one), so a tap where ⚙️ was only brings them back. The browser picks a tap's click target only after `pointerup`, when the button is back already, so a click on a button the pointer didn't come down on is dropped.
- **What stays up:** a button the mouse is on (`tooltip-hover`) or that has the keyboard's focus (`:focus-visible`), and 🔥 while its connection is down (`multiplex-disconnected`), or nobody would notice. A focus left by a tap or a click holds nothing: on a touch screen it would never go.
- **The specs keep them:** Cuprite counts a faded button as invisible, so `spec_helper.rb` sets `window.CONTROLS_STAY` on every page of every session (Ferrum's `extensions`). The `fading controls` example in `index_html_spec.rb` turns it off and shortens the delays (`window.CONTROLS_MS`).

See [the corner buttons fade out](decisions/2026-10-31-the-corner-buttons-fade-out-and-come-back-on-a-tap.md).

**The overlays are native `<dialog>`s** (in `style/body-controls.html`), opened with `showModal()`. 🔑 opens the password prompt (focuses its field) the first time on a device, and 🚀 the „wer scrollt?" choice, and on the clients the guest invitation (guest mode); self mode announces the coming song as a toast instead (see [Self-scroll announcement](#multiplex-live-sync) below), not a dialog. ⚙️ opens a settings dialog (a „Farben" `<select>` of colour schemes with five colour pickers under it, see [Colours](#colours), a „Schriften" list of radio buttons, one column for the titles and one for the text, and an „Akkorde anzeigen" checkbox); the multiplex status button opens a dialog with the connection/role status spelled out in words. A YouTube link on a slide opens a video dialog (see the links below). The QR, choice, invite, settings, video, update and multiplex-status dialogs all focus their title (`tabindex="-1"`, no ring), so a screenreader starts there and a phone shows no keyboard. Two things `showModal()` leaves to us, for every dialog: Reveal listens for keys on the document, where they still arrive from inside a dialog — so each dialog stops `keydown`/`keypress` from propagating, or the arrow keys would page the deck behind it and Esc would open Reveal's overview — and a click on the backdrop lands on the `<dialog>` itself, which closes it.

**Space on a focused button presses that button, and only that** (`keyboardCondition`, set with `Reveal.configure` on load): Reveal used to turn the page as well, so Space after 🚀 both ended live scrolling and moved on. The exception is a focus nobody can see: a mouse click leaves the button focused without a ring, and there Space blurs it and turns the page, as the one clicking expects. Whether the ring shows is read on `focusin`, because Chrome turns `:focus-visible` on as soon as any key is pressed. Inside a `<dialog>` this doesn't come up at all — the dialog stops the keydown before Reveal ever sees it, so Space on the settings checkbox or select just does the native thing.

**The buttons' labels are their tooltips.** Each control's `.visually-hidden` text is shown as a tooltip on hover and on keyboard focus. On hover by a mouse only: where there is hover (`(hover: hover)`, so a tap on a phone shows nothing), and on `pointerenter` with `pointerType` `mouse`, not `mouseenter`. A touch screen that also hovers makes up mouse events after a tap, and that mouse never left: the tooltip stayed, and held its button up while the others faded. Esc hides it without opening Reveal's overview, any other key hides it too, and it stays hidden until the pointer leaves or the focus moves.

**A slide's links never take the song book's tab away** (`external_links`, `lib/build_helpers.rb`, in `post_process_index`; not `print.html`). Coming back to the book meant loading it anew: slow on a slow connection, impossible without one, and a page with a session's socket open is often kept out of the back/forward cache. A YouTube video (`youtube.com/watch?v=…`, `youtu.be/…`: „Lied auf YouTube", a tutorial, an interpretation) gets its player's address as `data-video`, from `youtube-nocookie.com`, so that a visit to the book sets no YouTube cookie, just as it asks Google for no font. A click plays it in `#video-modal` (`body-controls.html`), titled with the link's text, whitespace collapsed: Pandoc wraps its lines, link texts included. The iframe (`allowfullscreen`, `autoplay`) is made as the dialog opens and dropped as it closes: the video stops with it, and nothing loads while none is open. A click with a modifier key still follows the link. Served from an IP address (`127.0.0.1`, or a phone reaching `./dev` over the LAN), every video reads „Dieses Video ist nicht verfügbar": YouTube refuses a player whose referrer is an IP. `localhost` and songs.josh.ch play. Any other link (the tab sources, …) opens in a new tab (`target="_blank" rel="noopener"`). Embedding them is no option: YouTube's own pages and Ultimate Guitar refuse to be framed (`X-Frame-Options`, `frame-ancestors`). Reveal's own lightbox (`data-preview-link`) was the other option and was rejected: its iframe has no `allowfullscreen`, its buttons no labels and its message is English, and a follower's `Reveal.setState` closes it with every step of the scroller. `spec/browser/index_html_spec.rb` (`links`) covers the dialog with blank pages in place of YouTube's, so nothing leaves the machine; `spec/unit/external_links_spec.rb` the addresses, the golden `infos_ueber_das_lied.html` the markup. See [decisions/2026-11-12-a-slides-links-never-take-the-song-books-tab-away.md](decisions/2026-11-12-a-slides-links-never-take-the-song-books-tab-away.md).

**Chords are real `<button>`s** (`chord_buttons` at build time, `style/chords.js` for the fingering), the copies in a slide's [next-line preview](#next-line-preview) included. The `<code>` inside is the coloured pill; the button shows nothing of its own (`all: unset` in `shared.css`), so the focus/hover ring is drawn around the pill. Tab, Enter and Space are the browser's own: Enter or Space opens the fingering, and the tooltip is read out as it appears (`aria-live`); `chords.js` only adds `aria-expanded`/`aria-controls`. Space on a chord focused by a mouse click turns the page, like on any button (see above). Hiding the chords in ⚙️ hides the buttons too, so they leave no empty Tab stops. The tooltip shows the guitar tab (`|E A D G B e|`, preferring a song's own Spielhinweise legend over the built-in `DEFAULT_CHORDS` fallback) beside a ukulele tab (`|G C E A|`, standard re-entrant tuning) from the separate `UKULELE_CHORDS` dictionary — side by side rather than stacked, since a slide has more spare width than height. The chord name only appears once, on the guitar column's own `Name |…|` row; the ukulele column (no per-song override — songs never document their own ukulele voicing) is just `|…|`, and a chord missing from `UKULELE_CHORDS` falls back to a single guitar-only column.

**The fonts are the reader's own.** One list of radio buttons, a font to a row, labelled with a picture of the font's name set in it (`style/fonts/samples/<id>.png`, white on transparent, darkened on a light background), with two radio buttons in each row: „Titel" sets the slides' headings (`--r-heading-font`), „Text" everything else on them (`--r-main-font`), and every font is on offer for either. Opening the dialog downloads the 20 small pictures (lazily, once it opens) and no font. The list scrolls, its column headings stay on top, and it opens scrolled to the first font picked down the list. Its first row, „Passend zum Thema" (`''`), is the [colour scheme's](#colours) own pair, which follows the scheme as it changes; a font picked stays across every scheme (someone who needs Atkinson Hyperlegible to read keeps it). `bundle exec rake fonts:samples` renders the pictures in headless Chrome from the rows themselves (the `img`'s `src` and `alt`, the radio buttons' value) with the book's own `@font-face` rules and `night.css` variables, and fails on a font that doesn't load. Either way `<body>` carries the font's id, `data-title-font`/`data-text-font` (`body-controls.html`: the reader's pick, or the scheme's `--theme-title-font`/`--theme-text-font`), for rules in `night.css`, where each font's family stack is written once (`--font-<id>`). Headings ask for a font's 700 where it has one; one with only a 400 is set in it as it is (`font-synthesis: style`, no fake bold). The pick is kept in `localStorage` (`title-font`, `text-font`); like the colours, it is applied as the page is parsed, so the slides are fitted in it from the start. The chords in the lyrics (the pills, `button.chord code`) wear the text's font, whichever it is, the picture fonts included: whoever picks hieroglyphs for a joke gets them in the chords too. Code blocks keep `--r-code-font`, monospace, and so does the chord tooltip: their fingerings' columns only line up when every letter is as wide. The dialogs and controls keep their own `sans-serif`, and `print.html` its serif theme. A stored font the book no longer offers falls back to the scheme's. `slide-zoom.js` needs nothing for a font change: a slide's size changes as the font arrives, and its observer fits it anew. Not synced over multiplex. See [decisions/2026-11-11-each-reader-picks-a-font-for-the-titles-and-one-for-the-text.md](decisions/2026-11-11-each-reader-picks-a-font-for-the-titles-and-one-for-the-text.md) and [decisions/2026-11-12-one-font-list-for-titles-and-text-schemes-bring-a-pair.md](decisions/2026-11-12-one-font-list-for-titles-and-text-schemes-bring-a-pair.md).

**The background is the reader's own too.** ⚙️'s „Hintergrund" (beside „Schliessen") opens a dialog of its own, `#background-modal`: in the settings, after the colour schemes came, it no longer fitted a phone held sideways. The settings close first, so the focus returns to ⚙️ afterwards, as the 📡 dialog's buttons do. „Bild wählen …" there opens the device's file picker (a hidden `<input type="file" accept="image/*">`), and the picture goes behind the slides: nothing is uploaded anywhere, there is no server for it. `body-controls.html` shrinks it on a canvas to 2048 px on its longer side (`BACKGROUND_SIZE`) and keeps it as a JPEG data URL in `localStorage` (`background-image`): a phone's photo is several times that, too large for localStorage, and under the veil nobody sees the difference. Like the colours, it is applied as the page is parsed: the data URL becomes the `src` of two `<img>`s in `#background-image`, a layer fixed to the screen behind everything (`z-index: -1`, the first element in `<body>`), and `body.custom-background` shows it. `<img>`s with `object-fit: cover` rather than a CSS background, so that the picture's own proportions can set its height (see the parallax below). A layer rather than the page's own background: on an iPhone in [Vollbild](#vollbild) the page is many screens tall, and `background-attachment: fixed` does nothing there. Over the picture lies a veil of the colours' background (`--background-veil`, `--color-background` made see-through with `color-mix`, on `<body>` where the colours are; drawn by `#background-image::after`, over both copies, `night.css`), so the lyrics stay readable on it, whatever the scheme. Graustufen turns the picture grey too, like everything else. How strong is the reader's to set, with „Schleier", a slider from 0 to 90% (70% unless set; `--veil` on `<body>`, kept in `localStorage` `background-veil`, the same for every scheme). The dialog has no backdrop, so the slides around it show what the slider does as it moves; it stays in place meanwhile (it used to step aside, all but the slider, which was more than needed). „Hintergrund-Bewegung (Parallax) aktivieren" (`localStorage` `background-parallax`, off unless checked, `body.background-parallax`) lets the picture glide up as one goes down a song's slides, all the way from its top edge at the screen's top on the song's title slide to its bottom edge at the screen's bottom on its last. The picture is as wide as the screen and as tall as its own proportions make it, but at least three tenths taller than the screen (a landscape one is cut off at the sides for that): a picture in portrait goes a long way, several screens' height on a desktop. `placePicture` (`body-controls.html`) sets `--parallax-y`, from 0 to 1, on every `slidechanged`, for a `translateY` of that share of the room left (`100cqh - 100%`: the layer is a size container, the screen) in `night.css`. With reveal.js's own timing (0.8 s, `cubic-bezier(0.26, 0.86, 0.44, 0.985)`), as the slide moves: two seconds, setting off gently and trailing behind the slide, were tried, and dragged once a picture in portrait had a long way to go. It never moves sideways: the book is mostly paged through the table of contents, from which a song's position in the deck says nothing (per song across, and across runs of ten songs, were tried). Another song, or the table of contents, starts at the top again: rather than sweep back up in one go, the layer holds two copies of the picture (`.background-picture`, the one shown `.current`), and the other one, already at the top, fades in over it (`.arriving`, 1.2 s); the table of contents and a song's title slide both sit at the top, so a jump between them changes nothing. A fade cut short by the next slide ends at once. Not reveal.js's own `parallaxBackgroundImage`: it counts the vertical slides of every song together and would have moved this book's picture by a pixel a slide, takes the picture's size in pixels and keeps it as the window turns, and animates `background-position`, which repaints the whole picture every frame. The picture is placed before it may glide (`placed`), so a reload shows it in place, not on its way there. With `prefers-reduced-motion: reduce` it neither glides nor fades. The table of contents' own background colour would show over it, as a band (the filter bar) and as a column at the rows' ends (the fading overlays): with a picture, the filter bar wears the veil and blurs what scrolls under it, and a long title fades out by its own letters (`background-clip: text`, which leaves the focus ring alone), in a session before the ❤️ and its count rather than under them. „Entfernen", „Schleier" and the parallax checkbox show only with a picture; „Entfernen" takes it away again (the veil and the movement stay as set) and moves the focus to „Bild wählen …". A file the browser can't decode, or a picture that couldn't be stored (site data blocked, storage full: it then shows until a reload), says so in a line under the buttons. Not synced over multiplex, and not in `print.html`. `spec/browser/index_html_spec.rb` (`background image`) covers it. See [decisions/2026-11-12-each-reader-may-put-a-picture-of-their-own-behind-the-slides.md](decisions/2026-11-12-each-reader-may-put-a-picture-of-their-own-behind-the-slides.md) and [decisions/2026-11-12-the-background-glides-up-a-song-by-our-own-parallax.md](decisions/2026-11-12-the-background-glides-up-a-song-by-our-own-parallax.md).

**Storage is optional:** with site data blocked, touching `localStorage` or `sessionStorage` throws, so every access is wrapped; the colours and fonts then change without being remembered.

## Colours

**The colours are the reader's own, like the fonts.** ⚙️'s „Farben" select offers schemes — „Dunkel" (the night theme's own, the default), „Hell", „Kontrast", „Graustufen", „Papier", „Nachtblau", „Ozean", „Lagerfeuer", „Sonnenuntergang", „Militär", „Terminal", „Rosa" and „Kunterbunt" — and „Eigene", and under it five colour pickers (`<input type="color">`): „Hintergrund", „Text", „Titel" (the headings, `em`, the next-line preview's heading), „Links" (the TOC's entries, the resource links, the chevrons) and „Fett" (`strong`). There is no dark and bright mode any more; Hell is one scheme among the others.

- **Five colours, everything else mixed from them.** `night.css` declares `--color-background`, `--color-text`, `--color-title`, `--color-link` and `--color-bold` on `body` — Dunkel's by default, another scheme's under `body[data-theme="…"]` — as `#rrggbb`, the only form a colour picker takes. From them, also on `body`, it sets the theme's own variables (`--r-background-color`, `--r-main-color`, `--r-heading-color`, `--r-link-color`, …) and mixes the rest with `color-mix()`: the dialogs, the toast and the tooltips (`--color-surface`, `--color-field`, `--color-control`, `--color-border`, a shade of the text over the background), the artist line (the title's, toward the background), the next-line rule, the TOC filter bar's line. A new colour on the page should be mixed from these too, not written down. A scheme is a rule in `night.css` — five colours, and, where it has a pair of its own, `--theme-title-font`/`--theme-text-font` by their ids (Montserrat and Open Sans otherwise; see the fonts in [Keyboard and dialogs](#keyboard-and-dialogs)) — and an `<option>` in `body-controls.html`; the theme spec checks every option against its pickers. A scheme may go beyond them where colours alone can't say it: Graustufen greys out the whole page, chord pills and emoji included, with `filter: grayscale(1)` on `<html>` (the root, which a filter doesn't make the containing block of what is fixed), and Kunterbunt's titles are Nabla, a colour font (in colour where the browser renders COLRv1, Chrome and Firefox; in the title colour elsewhere).
- **What can't be mixed** depends on whether the background is light: `body.theme-light`, set by `body-controls.html` from the background's luminance (WCAG's measure: black stands out more on it than white). It darkens the white font samples, gives the code blocks and the chord tooltip a deeper paper, and the 🔥 badge its idle grey and its following ring a darker blue. The chord pills keep their colours on every background.
- **A colour picked makes them the reader's own:** the select switches to „Eigene", `body` gets `data-theme="custom"` and the five as inline custom properties, the four not picked taken over from the scheme shown until then, its fonts too. What goes beyond the five (Graustufen's filter) stays with the scheme. It happens as the picker is dragged (`input`), not once it closes. Picking a scheme again leaves the reader's own be: „Eigene" brings them back.
- **Kept per device** (`localStorage` `theme`, the scheme's value, and `theme-colors`, the reader's five and the fonts they came with, as JSON), applied as the page is parsed, so the slides never show in another's colours first. A stored scheme the book no longer offers, or stored colours that aren't five `#rrggbb`, fall back to Dunkel. Not synced over multiplex. `print.html` keeps its serif theme.

## Vollbild

**↕️, top right, toggles full screen; a second press leaves it.** Where the browser has the Fullscreen API (a desktop, Android, an iPad: `document.fullscreenEnabled`, or its `webkit` form), ↕️ uses it on `<html>`, and `aria-pressed` follows `fullscreenchange`. While on, ↕️ wears a ❌, to say a press now leaves full screen. Started from the home screen (`navigator.standalone`, `display-mode: standalone`), the book has no bars to hide, and ↕️ stays hidden.

**On an iPhone, ↕️ asks for a swipe instead.** Safari there has no Fullscreen API for a page, but it hides its bars once a finger scrolls the page itself, which never happens in the deck: the page is one screen tall, and `.reveal` has `touch-action: pinch-zoom` (Reveal 6 reads swipes from pointer events, whose `preventDefault` stops no scrolling, so the CSS is all that does). So ↕️ opens the runway (`#fullscreen-runway`, `body-controls.html`):
- `html.fullscreen-runway` (`night.css`) lifts Reveal's `overflow: hidden`, pins `.reveal` with `position: fixed`, and the runway over it makes the page many screens tall: „Wisch mal runter!", with arrows on the way. Its title and ✕ sit in a sticky header, so ✕ stays at hand while the page scrolls. Its first screen is `100svh` high, the height with Safari's bars shown, so its last lines don't end up under the bottom bar.
- When the bars go, the window gets taller (`innerHeight`, read on `resize`, `scroll` and `visualViewport`'s `resize`). A 🎉 says so („Gut gemacht! …") and waits for OK (or Esc). Held upright, all of it fits one screen, an iPhone SE's included; held sideways (`(orientation: landscape) and (max-height: 500px)`, `night.css`), the picture goes beside the text. Should it still not fit (a larger text size, say), it scrolls in itself, like the table of contents (see `holdPage` below), from its top: two `1fr` grid rows centre it, not `align-content`, which pushes what doesn't fit past the top, out of scrolling's reach. It used to be `touch-action: none`, trusted to fit; on a phone held sideways the 🎉 ran off the top and OK off the bottom, and nothing could reach them. Only then does it show the alternative: from the home screen the book opens without any bars, with a picture of Safari's menu (`style/zum-home-bildschirm.png`, loaded lazily, so only by those who open the runway). Its `src` reads `{{assets}}zum-home-bildschirm.png`: `post_process_index` replaces `{{assets}}` in `body-controls.html` with the same `assets:` prefix as the other files, since the build and the spec fixtures serve `style/` from different paths. Then the runway fades out, but **it keeps its height and the scroll position**: a page back to one screen would scroll to the top, and Safari would bring its bars right back. Back in the deck, nothing may scroll the page, so the bars stay away. Reveal's keys don't, and on the deck `touch-action` keeps the fingers off it, but it reaches neither a code block (Reveal's theme gives `pre code` `overflow: auto`, a scroll container of its own) nor the corner buttons beside the deck: a swipe down there scrolled the page up, and the bars came back. So while the room is kept, `holdPage` cancels every one-finger `touchmove` on the document, except in the table of contents, a dialog, the settings' font list or the 🎉 that holds more than fits (a font list that doesn't leaves the swipe to its dialog); these get `overscroll-behavior: contain` (`night.css`), so a swipe past their ends stays with them. A tap does it too, in the strip Safari's bottom bar leaves behind: the bars come back, and the button there never hears the tap. So 🔥 and ⚙️ rise by as much as the window grew (`--runway-lift`, set in `check()`); only the top and bottom bars together are measurable, so that is a little more than the bottom bar alone. (📖 brought them back by following its link, see [Keyboard and dialogs](#keyboard-and-dialogs).)
- A second press of ↕️, the bars coming back (a tap on Safari's address strip) or a turned phone (another width) give the room back. A pinch-zoom shrinks `innerHeight` too and is ignored (`visualViewport.scale`). Esc or ✕ close the runway before the swipe; like the dialogs, it keeps its keys from Reveal.
- `?runway` in the URL forces the runway in any browser, to try it on a desktop, and for the specs.

The fit follows: `slide-zoom.js` watches the deck, not `<html>` (see [Slide layout and fit](#slide-layout-and-fit)). `spec/browser/index_html_spec.rb` (`Vollbild`) covers both ways, and the 🎉 on a phone held sideways, with a taller window standing in for Safari's bars going. See [the iPhone's Vollbild swipes the page itself](decisions/2026-10-28-the-iphones-vollbild-swipes-the-page-itself.md).

## Multiplex (live sync)

The presentation uses the [Reveal.js multiplex plugin](https://revealjs.com/multiplex/) via `multiplex.up.railway.app` so that the audience can follow along on their own devices. Two levels, two words: a **session** („Runde" on screen) is one evening, led by a **host** (Gastgeber), and within it the host starts **live scrolling** („Live-Scrollen") on one song at a time, and either scrolls it or hands the scrolling to a guest for that song. It is not a running mirror of the host's every move.

The code is the second `<script>` in `style/body-controls.html`; the server is a pure relay (one event, `multiplex-statechanged`, forwarded to everyone but the sender when `sha256(secret) == socketId`, no storage). Five message types ride on that one event: `host` (the host's heartbeat), `state` (from whoever scrolls), `volunteer` (from a guest offering), `wish` (a device's song wishes, see [Wishes](#wishes-the-%EF%B8%8F-on-each-song)) and `end` (the host ended the session). In the code, a live scroll is `live` (`{ id, song, songTitle, mode, scrollerId }`). `body-controls.html` is spliced in *after* the build's `keyboard:`/`controls:` rewrites (see `post_process_index`), so its own `Reveal.configure` calls are not mistaken for Pandoc's init.

- **A session is kept on the device, not in the address.** Its secret arrives only once, as the `?live=` parameter of the host's QR code or typed in as its code (see [Joining by code](#joining-by-code)); the page stores it (`localStorage` `multiplex-session`). The relay channel is `sha256(secret)` (`style/sha256.js`, see [Session and secret](#session-and-secret)). So the session outlasts a reload, a discarded tab, a new tab and the song book reopened from the home screen, and an address bookmarked or added to the home screen meanwhile carries none. **`?live=` (and the `qr` marker) leave the address as the page is parsed, before Reveal starts** (the first lines of the multiplex `<script>`, handing them on as `window.MULTIPLEX.join`). Reveal writes the address itself, at most once a second, and a write it deferred carries the query string of the moment it was asked for: stripped on load, `?live=` came back a second later, and a guest who had left the session was back in it after a reload. Kept in the address for good, it got dropped again the same way. The QR spec records every address written and allows none with `live=`. A device in no session opens no socket at all, so a plain visit to the song book is never locked to anybody's evening, and two evenings at once never touch each other. **A session nothing was heard of for 12 hours is a past evening** (`SESSION_TTL_MS`, against `seenAt`, which every message heard and every heartbeat sent renews): on the next load it is forgotten. A guest leaves of its own accord with 🚪 „Runde verlassen", and stays where it is.
- **Logging in as host** (🔥 › 🔑 „Als Gastgeber anmelden") asks for the password once per device (`localStorage` `multiplex-authed`; the host's `hostClaim` is kept in `multiplex-session`, with the session). Without a session it opens a new one: a fresh secret, generated in the browser, and, once the „Lieder von" dialog is confirmed (see below), its QR code opens, since nobody is in the session yet (a takeover doesn't open it: the guests are in already). Only the host sees 🚀 („Live-Scrollen starten"/„beenden", enabled only on a song, elsewhere disabled with a hint saying why) and 🏁 „Runde beenden". 🔗 is offered to the host and to everyone else in the session, 🚪 „Runde verlassen" to everyone in it but the host; a plain visitor sees only 🎟️ „Mit Code beitreten", 🔑 and the line „Scanne den QR-Code eines Gastgebers oder gib den Code der Runde ein, um mitzulesen". Every button closes the 🔥 dialog before opening its own, so the focus returns to 🔥 afterwards.
- **The host is the single authority, and the role is taken over, not handed on.** In a session, 🔑 reads „Gastgeber übernehmen": whoever logs in last leads. Its claim is above every claim heard in the session (`heardClaim`, not just its own clock, which may run behind the old host's). The old host steps down when it hears the higher claim, with the toast „Jemand anderes ist jetzt Gastgeber", and stays in the session as an ordinary participant (a duplicated tab, with an equal claim, settles by `from`). A song being live-scrolled carries on as it is: the new host inherits `live`, and if the old host was scrolling it scrolls on, as a guest would. There is no co-host and no „abgeben". See [each evening is its own session, led by a host](decisions/2026-10-31-each-evening-is-its-own-session-led-by-a-host.md).
- **Whose songs the evening has.** The moment a host has logged in (or taken over), the „Lieder von" dialog opens by itself, with the Gastgeber as checkboxes, for the host to say who is here tonight; confirming it with „OK" closes it, and for a new session the QR code follows (`qrPending`, `showQrAfterHosts`, on the dialog's `close`; where no song names a Gastgeber, the QR code opens at once as before). Every list in the session then shows only the songs of the ticked hosts (all of them until the host unticks the ones who are absent; see above for what that does to the list). The table of contents' „Lieder von: …" button reopens the dialog, for the host to change the choice and for the guests to read it (their checkboxes are disabled). `present` rides on the heartbeat of the host, is stored with the session, goes along with a takeover, and is applied on every device (`applyTocFilter`); only the host's checkboxes are enabled. So does the host's Sprache and Genre (`filter`, `{ sprache, genre }`, `''` for „Alle"): a value the host picked holds on every device, its select disabled for the guests; one left at „Alle" is each guest's own (see the TOC filter above). A new session starts unfiltered. Leaving the session gives the filter back, nothing filtered. See [the host sets who is present for the whole session](decisions/2026-10-31-the-host-sets-who-is-present-for-the-whole-session.md) and [the host filters the table of contents for the whole session](decisions/2026-11-11-the-host-filters-the-table-of-contents-for-the-whole-session.md).
- **Wishes, the ❤️ on each song.** In a session, a guest says which songs they would like to sing: a ❤️ in the song's row of the table of contents and on its title slide (the same `button.song-wish`, built by `wish_button` in `lib/build_helpers.rb` with the song's slug as `data-song` — `inject_toc_filter` adds the TOC one from the entry's own `#/<slug>` link, `inject_song_wishes` the title slide's from the `section.level1` id; not the Introduction, not `print.html`), with the count of devices in the session that wish it. A press toggles this device's wish (`aria-pressed`; a mistap is undone by a second press). `style/wishes.js` owns what shows — the heart's fill, the count (from 1 on; the `.visually-hidden` label reads „Lied wünschen, 2 Wünsche" for a screen reader) and whether the hearts show at all (`body.wishes-active`, only in a session: outside one there is no room to count, so the TOC stays as it was) — through `window.songWishes` (`onToggle`, `setMine`, `setCounts`, `setActive`); `body-controls.html` owns the room. **Every device tallies for itself, no host is asked:** each sends its whole set of wished slugs as a `wish` message — never a `+1`, which a lost packet would falsify — on every change, on connect, and again every round (`WISH_SYNC_MS`, 8 s; `window.MULTIPLEX.wishSync` for the specs; `scheduleWishRound`, started by `join`) while it has any; each keeps the sets it hears per sender (`wishSets`) and drops a sender unheard for three rounds — a tab that was closed. So a takeover or a host's reload loses nothing, and a latecomer is counted, and counts everyone, within one round. The device's own wishes (`myWishes`) are stored with the session (`persistSession`) and survive a reload; leaving or ending the session forgets them (`forgetWishes`) — the next evening starts from none. Layout in `shared.css`, colours in `night.css`. In the TOC the button is absolutely positioned at the row's right edge, over the row's full height, the heart rightmost and its count to its left (`flex-direction: row-reverse`), so the hearts stand in one column with or without a count. A long title runs on underneath it: the button wears the list's own background (`--r-background-color`, whatever the [colours](#colours)) in a gradient that is transparent at its left edge (`border-box`, or the button's 2px transparent border showed the gradient's transparent start and the title peeked out beside the heart), so the title fades out just before the count. It takes over from the row's own fading overlay, which is off in a session (it comes after the button and would cover it; see the TOC filter's Styling). See [decisions/2026-11-11-guests-wish-for-songs-with-a-heart-counted-per-session.md](decisions/2026-11-11-guests-wish-for-songs-with-a-heart-counted-per-session.md). `spec/browser/song_wishes_spec.rb` covers it, the goldens `toc.html` and `imagine_title.html` pin the markup.
- **Starting live scrolling:** 🚀 opens a choice: „Ich selber möchte scrollen" or „Ein Gast soll scrollen". Only the host starts and ends it, and names the scroller.
- **Every role survives a reload, not just the host's.** `senderId` — normally a fresh random value per page load — is itself kept in `sessionStorage` (`multiplex-sender-id`), so a reloaded guest scroller is still recognised as the same `scrollerId` the host already named, instead of coming back as a stranger and dropping to a mere follower. It stays per tab on purpose, unlike the session: two tabs sharing an id would each drop the other's messages as their own, and two host tabs could never settle which leads. The session's live scroll, the heard claim and whether this tab was the one scrolling are stored with it (`persistSession`, called in `reconcileLive`/`concludeLive`/`releaseSilently` and wherever else they change) and reapplied immediately on load, before the next heartbeat would otherwise re-establish them — so a follower or a scroller doesn't flash back to free navigation for the few seconds in between. A host reopened in a new tab comes back under a new sender id; if it was scrolling (`scrolling`), it names itself scroller again, and its next heartbeat tells the room. A guest scroller can't do that — the host names the scroller — and the host gets the „Keine Rückmeldung mehr vom scrollenden Gerät" toast instead (see below).
- **Guest delegation.** In guest mode everyone in the session is asked „«Song» wird als nächstes gespielt. Möchtest du das Live-Scrollen übernehmen?". The first „Ja" the host hears wins — it echoes the chosen `scrollerId`, the other invites close, and everyone (the host included) follows the guest. A single authority means two near-simultaneous „Ja"s cannot both take over. The moment a scroller is named, whoever had been invited for that live scroll (`invitedFor`, `volunteeredFor` in `reconcileLive`) gets a one-off toast on `#multiplex-toast`: the winner „Danke für deine Bereitschaft! Lass uns gleich starten…", a volunteer who lost the race „Oh, das wäre nett gewesen – aber jemand anderes scrollt bereits!", and everyone else who was asked but didn't win (declined or never answered) „Es geht gleich los!". The host gets its own toast the instant it accepts a volunteer — „Jemand hat sich bereit erklärt, es geht gleich los" — instead of a silent status-line change. A latecomer who was never invited sees none of these.
- **Self-scroll announcement.** In self mode the host scrolls, so there is nothing to volunteer for; each device that is present as the live scroll starts is shown a toast on `#multiplex-toast` — „Es geht gleich los!" / „Das nächste Lied ist «Song»." (once per live scroll, `announcedFor`) — and then follows along, same as any other toast: no OK button, it just fades after its own timeout. The opening `host` message carries `fresh: true` and the heartbeats do not, so a latecomer who only ever hears a heartbeat just follows — as with the guest invite. The host sees no such toast.
- **The scroller is locked to its song** (`SCROLLER_KEYS` disables the horizontal keys plus Home/End — reveal.js binds those to "next slide"/"first slide"/"last slide", which reached the snap-back below too, but only after already jumping and losing the scroll position (v reset to 0). Space/Shift+Space default to the same escape-prone `next()`/`prev()`, so `SCROLLER_KEYS` remaps them instead of disabling them outright: they call `Reveal.down()`/`Reveal.up()`, the same calls the (already safe) vertical arrow keys make, stepping within the song and no further. A capture-phase guard swallows horizontal *swipes* before Reveal sees them — Reveal has no vertical-only touch option, so this keeps vertical scrolling while a left/right swipe does nothing. It swallows only the swipe's moves, never its `pointerup`/`pointercancel`: Reveal 6 keeps every finger down in a map until it hears it lift, and one that never did stayed there for good, so every later swipe counted as two fingers (a pinch) and the deck took none until a reload; the `swipe` spec helper gives each swipe a `pointerId` of its own, or the next one overwrote the stale finger and hid this; a link that still leaves the song snaps back on `slidechanged`). It may only scroll up/down within the current song; to move on, the host ends the live scroll. **No overview while a song is live-scrolled**, for the scroller or any follower (`applyNavMode` sets `overview: false`, and `true` again once free): the scroller's showed the neighbouring songs it couldn't reach, and a click on one jumped there and was snapped back. An overview still open as live scrolling starts is closed first, outside the snap-back (`applyingRemote`), and *before* the switch, since Reveal's `deactivate()` does nothing once `overview` is false. See [decisions/2026-10-31-no-overview-while-a-song-is-live-scrolled.md](decisions/2026-10-31-no-overview-while-a-song-is-live-scrolled.md).
- **Everyone else follows, with no opt-out.** A follower's keyboard, touch and controls are off and its view is snapped to the scroller — there is no more „browse freely" (👣 is gone). 📖 is hidden too, for the scroller as well as every follower (`applyNavMode`): without it, clicking through to the TOC would still be undone by the `slidechanged` snap-back, but not before an unwanted flash. A follower that hears nothing about the live scroll for three heartbeats frees itself rather than freeze; the host's next heartbeat locks it again. The host is exempt from this self-release, even though it is itself a "follower" of a guest it delegated to: a flaky connection to the *guest* used to silently eject the presenter (as the host was then called) from its own session three heartbeats later — the ❌ vanished and 🚀 reverted to „Live-Scrollen starten" — while the guest, and everyone else still locked to it, carried on regardless, now with nobody able to end it. See [the presenter must not self-release while following its own delegate](decisions/2026-10-04-presenter-must-not-self-release-while-following-its-own-delegate.md).
- **Heartbeat:** the host repeats its `host` message for as long as it hosts — who hosts (`claim`), who is present (`present`), the Sprache and Genre the lists show (`filter`) and what is live-scrolled, if anything (`live`, or `null`) — and the scroller its `state`, every 2 s (`HEARTBEAT_MS`; the specs shorten it through `window.MULTIPLEX.heartbeat`), and again right after a reconnect. That is how someone who opens the page mid-song, or comes back from a dead spot, catches up — the relay hands out no last state — and how a host that was offline while it was taken over learns of it within one beat. A latecomer who arrives while a guest is still being sought is invited too; once a scroller is named, latecomers just follow.
- **Only the slide is sent** (`stateToSend`): indices, never `paused` (a scroller's B blacks out its own screen only). The overview needs no such care any more: there is none while a song is live-scrolled (above).
- **A position belongs to its live scroll.** A follower follows only a position heard for the live scroll under way (`scrollerState`), and the host announces a live scroll before it sends where it scrolls it from (`startLive`): a follower drops a position for a live scroll it hasn't heard of. Before, the room went first to where the last song had ended, and on to the next one only with the next heartbeat.
- **Ending live scrolling** drops everyone — the host included — back onto the table of contents (`gotoToc`, the `#TOC` slide) and shows a toast (`#multiplex-toast`, `aria-live`): „Du kannst jetzt wieder frei navigieren" to everyone who was in it, and „Vielen Dank fürs Scrollen!" on top of that for the guest who scrolled. A silent timeout (lost connection) frees a follower where it stands, without the jump. The end rides on every heartbeat that follows (`live: null`), so a single lost packet strands nobody — it used to be a one-off message repeated twice, see [ending a session repeats its broadcast](decisions/2026-10-04-ending-a-session-repeats-its-broadcast-to-survive-one-dropped-packet.md).
- **Ending the session** (🏁, host only) sends `end` — now, and twice more over the following second (`endSession`), since there is no heartbeat left to carry it. Every device in the session leaves it (`leaveSession`): it forgets the session, its socket closes a moment later, „Die Runde ist beendet" shows, and whoever was live-scrolling lands on the table of contents as above. Only the session's current host can end it: an `end` with a claim below the heard one is ignored.
- **Status button** (🔥, bottom left, `#multiplex-status-button`; a campfire, for the evening's songs strummed together, where a 📡 used to stand): a graphical, role-aware stand-in for what used to be a floating text line — inspired by the sibling project `axipedia`'s multiplex "lamp" (`revealjs/plugin/multiplex/multiplex.js` there). A badge on the 🔥's corner says who's driving at a glance: a filled dot when this device moves the deck for everyone (self-scroll host, or a guest scrolling for the room), an open ring when it's locked to someone else's scroll instead (an ordinary follower, or the host after delegating to a guest), amber while a host waits for a guest to volunteer, grey when idle, and a diagonal strike over whichever shape applies when this device is in a session but its socket is disconnected — colour is never the only signal (WCAG 1.4.1), matching axipedia's own reasoning for the same choice. A click opens the live-scroll dialog, with the same state spelled out in words, above its buttons. That text — „Du scrollst live" / „Warte auf Gast …" / „Gast scrollt" / „Du bist Gastgeber" for the host, „Du scrollst für alle" for the guest, „Folgt" for a follower, „Kein Live-Scrollen aktiv" for anyone else in a session, „Verbinde …" / „Keine Verbindung" before the socket is up and after it drops, and „Keine Runde" outside one (`statusText()`) — also sits, invisibly, as the button's accessible name (`#multiplex-status`, `role="status"`, `.visually-hidden`) for a screenreader to announce as it changes. It is the ongoing truth, for as long as a condition lasts; `#multiplex-toast` layers the *moment something changes* on top: „Du bist jetzt Gastgeber" / „Jemand anderes ist jetzt Gastgeber" on a login and a takeover, „Verbindung verloren" / „Wieder verbunden" on the socket's own `disconnect`/`connect` events (while a song is live-scrolled), and — host only, since it no longer self-releases (above) — „Keine Rückmeldung mehr vom scrollenden Gerät – du kannst das Live-Scrollen bei Bedarf beenden" the moment the scroller it handed the song to goes stale, „Das scrollende Gerät ist wieder verbunden" once it resumes (neutral about who scrolls: after a takeover it can be the old host). The watchdog driving that pair ticks on a fixed 500ms, independent of `cfg.heartbeat` — a spec shortening the heartbeat to test it must keep 3× that comfortably above 500ms, or "fresh again" is never observable (`body-controls.html`).
- **QR code** (🔗, in the 🔥 dialog, for anyone in a session): the session's address, `?live=<secret>&qr=1`, so whoever scans it is in — and a neighbour can let a latecomer in, not only the host. The `qr=1` marker makes the scanning device show its own code right away, titled „Du bist dabei!" with „Lass weitere Gäste diesen QR-Code scannen, damit auch sie mitlesen können." — without it, a guest who had just arrived would wonder what the code is for (`showQrModal(joined)`); through 🔗 or after a login it reads „Liederbuch öffnen" / „Scanne den Code …", for those reading it off that screen. Below the text, the session's code, for those who type it in instead ([Joining by code](#joining-by-code)). Both parameters leave its address as the page is parsed (above).

See [decisions/2026-09-30-live-scroll-sessions-presenter-delegates-to-a-guest.md](decisions/2026-09-30-live-scroll-sessions-presenter-delegates-to-a-guest.md) and [decisions/2026-10-31-each-evening-is-its-own-session-led-by-a-host.md](decisions/2026-10-31-each-evening-is-its-own-session-led-by-a-host.md).

### Session and secret

The build carries no multiplex pair. The host's browser generates each session's secret as it logs in (8 characters of Crockford's base32, `crypto.getRandomValues`, see [Joining by code](#joining-by-code)), and every device derives the relay channel from the secret in its address, `socketId = sha256(secret)` — all the relay checks before forwarding. The secret travels, not only the socketId: guests send too (a volunteer's „Ja", then the guest scroller's position), and the relay forwards nothing without it. So being in the session is having its secret, where before anyone could read the one pair from the page source.

`style/sha256.js` (`window.sha256Hex`) computes the hash, synchronously and in plain JavaScript: `crypto.subtle` is asynchronous and exists only in a secure context, so a phone reaching `./dev` over the LAN by IP address would have had no hash at all. The structure spec checks it against Ruby's `Digest::SHA256`.

Nothing is fetched from the relay: its `/token` would do exactly the same randomBytes-and-hash. On an iPhone a song book added to the home screen keeps its storage apart from Safari's, and a scanned QR code always opens in Safari: a guest who wants to follow in the home-screen app types the code there instead. A host who logs in inside the home-screen app stays host there.

### Joining by code

The secret is the session's code, short enough to read out and type: 8 characters of Crockford's base32 (the digits, and the letters but I, L, O and U, which pass for 1, 1, 0 and V), 40 random bits (`newSecret`, `body-controls.html`). The QR dialog shows it below the text, in two halves („Oder in 🔥 den Code eingeben: K7QM-2XRA", `#qr-code-line`), and a visitor types it in 🔥 › 🎟️ „Mit Code beitreten" (`#join-modal`). `readCode` takes it in any case and spacing, with or without the dash, and reads O, I and L as the 0 and 1 they look like. A session from before the codes (a 32-digit hex secret, gone with its evening) shows no code line.

A typed code can be mistyped, or be last week's, and a session that doesn't exist looks just like a quiet one: the relay keeps no list. So the device joins **on trial**: it opens the socket and waits to hear the session, which its host's heartbeat says every 2 s. The first message heard (`trialHeard`, in `onMessage`) keeps it in, closes the dialog and opens the QR dialog as „Du bist dabei!", as a scanned code does. Connected but unheard for three heartbeats, it leaves again without a toast (`leaveSession([])`) and says „Keine Runde mit diesem Code gefunden. Stimmt er?"; not even connected after eight, „Keine Verbindung. Versuch es nochmals, sobald du Netz hast." The dialog stays open for another try. Nothing is touched (`seenAt`) during the trial, so a reload meanwhile doesn't keep the session either.

40 bits are weaker than the 128 the secret had: the relay forwards every message to every socket under its `socketId`, so whoever listens there could search the codes for a matching hash offline. That gets them no more than the password in the page source does already. See [decisions/2026-11-12-a-sessions-secret-is-an-8-character-code-to-type.md](decisions/2026-11-12-a-sessions-secret-is-an-8-character-code-to-type.md). `spec/browser/index_html_spec.rb` covers it („a guest joins by the code under the QR code").

### Password

Default password: `guitar`. Override with the `MASTER_PASSWORD` env var at build time:

```bash
MASTER_PASSWORD=mypassword ./build
```

The password is embedded in the generated HTML (visible in source). This is intentional — the goal is only to keep the audience from accidentally becoming host, not real security.

## Offline: the service worker

**Once a device has opened the song book, it opens without the network.** `sw.js`, beside `index.html`, is a service worker: `./build` writes it from `lib/service-worker.js` (`service_worker` in `lib/build_helpers.rb`), and the page registers it once it has loaded (`body-controls.html`), so its downloads don't hold up a first visit on a slow connection. It keeps the page and every script and stylesheet the page loads from its own site, read off the page itself (`FILES`), so the list can't fall behind it. A reload, a tab iOS discarded in the background, the song book opened from the home screen, and a QR code's `?live=` address (any address of the page, whatever its query) all come from its cache, at once, with a slow connection or none. Only the relay's socket needs the network, and socket.io reconnects by itself. The fonts and the pictures (⚙️'s font samples, the Vollbild runway's) are kept as they are first asked for. A font is `immutable` in the browser's own cache too, so one loaded before the worker took over is still found offline.

- **A new build shows on the load after the one that finds it.** `VERSION` is a hash of the page and its files, so any change to them changes `sw.js`. The browser checks `sw.js` on every visit, and the new worker fetches the new files in the background (`cache: 'no-cache'`: an unchanged one comes back as a 304), takes over (`skipWaiting`, `clients.claim`) and deletes the old cache. The page on screen stays as it was. So after a deploy, the first visit still shows the old build and the second shows the new one. This is the price of not waiting for the network on every load, the opposite trade from the `no-cache` headers ([Cache headers](#cache-headers)), which only ever saved a stale copy, never the round trip.
- **A dialog offers the new build at once.** When a new worker takes over a page it was already controlling (`controllerchange`, with a controller at load, so not the very first worker), `#update-modal` opens: „Neue Version", „Eine neue Version des Liederbuchs ist da." and „Neu laden", nothing else. „Neu laden" writes the current slide into the URL (`writeSlideToUrl`, as on `visibilitychange`) and reloads, so the new build opens where the reader was; a session, its role and its live scroll survive a reload anyway. There is no „Später", and unlike the other dialogs a tap on the backdrop doesn't close it, or a stray one on a phone would. Esc still does (a modal dialog's Esc is the browser's own), and the next visit shows the new build then. Like the other dialogs, it focuses its title and keeps its keys from Reveal. See [decisions/2026-11-12-a-new-build-offers-itself-in-a-dialog.md](decisions/2026-11-12-a-new-build-offers-itself-in-a-dialog.md).
- **Not in `./dev`** (`./build --dev`, `window.SERVICE_WORKER = null`): browser-sync's reloads would show what the worker keeps. The page unregisters any worker instead. Nor where there is no secure context: a phone reaching `./dev` over the LAN by IP address has no `navigator.serviceWorker`.
- **To get rid of it,** deploy an `sw.js` that unregisters itself (`self.registration.unregister()` on `activate`). Deleting `sw.js` from the server leaves the installed workers running on the devices: the browser keeps a worker whose script it can no longer fetch.
- **Specs:** `spec_helper.rb` turns it off on every page (`window.SERVICE_WORKER_OFF`, through Ferrum's `extensions`, like `CONTROLS_STAY`), since its cache would outlast an example and serve the next. `spec/browser/offline_spec.rb` turns it on. It stands for offline by stopping the file server (`FileServer.stop`), since emulating the network on the page needn't reach the worker, which fetches from a target of its own. It also lets the worker's target run: Ferrum attaches to every new target with `waitForDebuggerOnStart`, but resumes only pages and iframes, and a paused worker never settles its registration. `spec/unit/service_worker_spec.rb` covers the file list and the version.

See [decisions/2026-11-12-the-song-book-opens-from-a-service-workers-cache.md](decisions/2026-11-12-the-song-book-opens-from-a-service-workers-cache.md).
