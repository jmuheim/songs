# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Record decisions in [`decisions/`](decisions/), one file per entry** — see [DECISIONS.md](DECISIONS.md) for the format, and use the `songs-log-decision` skill to add one. Never append to a shared list.

## What this project is

A guitar song book generator. Songs are written in Markdown with inline chord notation. A Ruby script compiles them into an interactive Reveal.js HTML slideshow (`index.html`) and a print-friendly version (`print.html`).

## Working agreements

These are not descriptions of how things happen to work — they are commitments to keep. Follow them without being asked.

- **Commit straight to `master`; no pull requests.** This is a small, private project, and a branch-and-PR round trip costs more than it catches. New work goes onto `master` with no question about the branch, but it is committed only once the user has looked at it: show what changed, take their corrections, and commit after their OK. When the main checkout is busy (another session, uncommitted work), work in a separate git worktree on a short-lived local branch there (git won't check out `master` in two worktrees at once), then rebase it onto `master` and fast-forward `master` to it. A fresh worktree lacks what is gitignored: create the multiplex credentials (`bundle exec rake multiplex:token`) and install the relay's dependencies (`npm ci --prefix multiplex-server`) before building or running the specs. Keep unrelated changes in separate commits. See [decisions/2026-10-28-commit-straight-to-master-no-pull-requests.md](decisions/2026-10-28-commit-straight-to-master-no-pull-requests.md) and [decisions/2026-10-29-commit-after-review-push-only-when-asked.md](decisions/2026-10-29-commit-after-review-push-only-when-asked.md).
- **Behaviour changes come with tests.** If you change the build pipeline, the chord regex, the multiplex logic, or anything in `style/*.js`, add or update the spec that pins that behaviour before considering the change done — and run `bundle exec rspec`. New behaviour with no covering spec is unfinished work. For the browser specs, follow the `songs-browser-specs` skill.
- **Keep the golden fixtures in sync.** `all-songs.md`, `index.html`, `print.html` and the fixtures under `spec/fixtures/` (except `golden/`) are build outputs — they are generated, not committed (gitignored; the specs regenerate the fixture HTML themselves). The one committed reference is `spec/fixtures/golden/`: when you change the markup or the generator, regenerate it with `bundle exec rake golden:update` in the same change — the golden specs exist to catch exactly the drift you'd otherwise leave behind.
- **One source of truth.** Don't copy logic that already lives in `lib/build_helpers.rb` (or anywhere else) into a second place. If the build and a spec both need a transformation, both call the same helper, so the spec tests what ships.
- **Skills are living artefacts.** The skills in `.claude/skills/` (`tab-to-song`, `songs-browser-specs`, `songs-log-decision`) describe real, current behaviour of this repo. When the song format, the build, or a workflow they document changes, update the matching skill in the same change. If a task reveals a repeatable workflow the skills don't yet cover, propose one.
- **Docs track reality.** This file and `README.md` must match what the code actually does. If you change a command, a dependency, or a default, update both.
- **Knowledge lives in the repo, not in a private store.** Record decisions, conventions, gotchas and working practices here, in [`decisions/`](decisions/), or in `README.md` — never in Claude Code's per-project memory. Repo files travel with the code, are reviewable, and are visible to everyone; a private memory is none of those. If something is worth remembering, commit it.
- **Push `master` only when asked, and only after a green local run; then watch CI.** A push deploys, so whether a commit goes live is the user's call, separate from their OK to commit it. After a commit, say how many commits `master` is ahead of `origin/master`. `bundle exec rspec` passes before every push. The push itself starts CI, which deploys to songs.josh.ch once its own run is green (`needs: rspec`, see [Deploy](#deploy)). A red run deploys nothing, so the site stays on the last green build. Watch it with `gh run watch <id> --exit-status`, and if it goes red, fix forward on `master` straight away. `master` has no branch protection and no required checks; this discipline is the gate.

## Build command

```bash
./build           # Build index.html and print.html
./build --deploy  # HTML + deploy to songs.josh.ch
./dev             # Watch, rebuild, and live-reload on every change (local only, no deploy)
```

Dependencies: Ruby 3.x, Pandoc (`brew install pandoc`), fswatch (`brew install fswatch`), browser-sync (`npm install -g browser-sync`).

The first build on a fresh clone needs local multiplex credentials — `build` refuses to run without them. Create them once with `bundle exec rake multiplex:token` (writes the gitignored `multiplex-token.json`). Deploys to songs.josh.ch happen from CI on every push to `master` once the suite is green (see [Deploy](#deploy)); `./build --deploy` remains the manual fallback.

> **Dev gotcha:** `./dev` passes `--no-ghost-mode` to browser-sync. Ghost mode (on by default) syncs clicks across all open tabs and interferes with the multiplex feature — it makes button presses appear to fire on all "clients" simultaneously during local testing.

## Deploy

Deploying is a CI job (`deploy` in `.github/workflows/test.yml`), not something a local save does. It runs **only on a push to `master`**, and only **after the `rspec` job is green** (`needs: rspec`) — so an untested commit never reaches songs.josh.ch. Its own `concurrency` group serialises deploys. The job generates a fresh multiplex pair, runs `./build`, and `rsync`s `index.html` + `style/` + `.htaccess` to the server (not `print.html`, matching the old manual deploy).

The server is reached with a dedicated ed25519 **deploy key** (secret `DEPLOY_SSH_KEY`), separate from anyone's personal key and locked on the server via `authorized_keys` to `rrsync` into `…/songs.josh.ch/` only — so the rsync target is relative. The host key is pinned in the workflow (no `StrictHostKeyChecking=no`); refresh it with `ssh-keyscan greip.uberspace.de` if the server ever rotates its key.

`./build --deploy` stays as the manual fallback: it rsyncs the same files from your machine using your own SSH access (absolute path), bypassing CI.

### Cache headers

The repo's root [`.htaccess`](.htaccess) ships with every deploy and tells Uberspace's Apache (`mod_headers`) to send `Cache-Control: no-cache, must-revalidate` for `.html`/`.css`/`.js`, and a year-long `immutable` cache for fonts. Without it, browsers fall back to heuristic caching of `index.html` and `style/*.css|js` — since those keep the same filename on every deploy, a cached copy never looks stale on its own, and phones with the song book added to the home screen (an even more aggressive webview cache) could sit on a build from weeks ago. `no-cache` still lets the browser keep a local copy; it just forces a conditional request every time, so an unchanged file comes back as a cheap 304.

## Song file format

Each song lives in `content/songs/<slug>.md`, where `<slug>` is its H1 lowercased, with `.`/`,`/`'` dropped, German umlauts transliterated (`ä`→`ae`, `ö`→`oe`, `ü`→`ue`, `ß`→`ss`), and the remaining spaces turned into underscores (everything else — `&`, `!` — passes through as-is): `# Family Portrait - P!nk` lives in `family_portrait_-_p!nk.md`, `# Knockin' on Heaven's Door - Bob Dylan` in `knockin_on_heavens_door_-_bob_dylan.md`, `# Über den Wolken - Reinhard Mey` in `ueber_den_wolken_-_reinhard_mey.md`. The H1 itself keeps its real spelling (punctuation and umlauts both) — only the filename is transliterated/stripped, to stay plain-ASCII-friendly in a shell. Structure:

```markdown
# Song Title - Artist Name

## Infos über das Lied

- Sprache: Englisch
- Genre: Mantra
- Gastgeber: Josua, Monika
- [Lied auf YouTube](https://youtube.com/...)
- [Source tab](https://...)

## Instructions

```
       |E A D G B e|
       |-----------|
A7sus4 |x 0 2 0 3 0|
```

## Section Name

Lyrics with [Chord] inline like this [Am] and here [G7].
```

- **H1** = `Title - Artist` (the literal separator is a space, a hyphen and a space — reserved, so a title may not itself contain that exact substring; `74-75`'s unspaced hyphen is fine). Drop the artist entirely — just `Title`, no trailing `- …` — when there's no specific one to credit: a traditional/folk song, written `Traditional` for an English title or `Traditionell` for a German one (the two forms this book already uses; any flag or other annotation that used to ride along in the parenthetical, e.g. `(Traditionell 🇨🇭)`, is dropped with it rather than kept on the bare title). One per file, shown as the slide title. **Nothing but blank lines may follow it before the first H2** — `validate_song!` aborts the build otherwise; a capo note or any other aside belongs in `## Infos über das Lied` instead (e.g. `- Capo: 3. Bund`).
- On a song's own title slide, `split_song_artist` (`lib/build_helpers.rb`, part of the shared pipeline below) splits that H1 back apart: the title stays in the `<h1>`, the artist becomes a sibling `<p class="song-artist">` right after it, styled smaller and a shade darker than the title (`style/shared.css` for size, `style/night.css`/`style/serif.css` for colour, per theme). A bare `Title`-only H1 (no artist) is left as a plain `<h1>`, same as "Introduction". This only touches each song's own `section.level1 h1` — never the deck's own title-slide cover (`section.deck-title-slide`).
- **H2** = section (each becomes a sub-slide)
- **Chords** use `[ChordName]` inline in lyrics
- An **`## Infos über das Lied`** section at the top holds the song's tags and its resource links together, authored in this shape directly (not assembled at build time): one `- Sprache: <value>` line, one or more `- Genre: <value>` lines (free text — keep the vocabulary consistent, e.g. `Deutsch` / `Englisch` / `Mundart` / `Pop` / `Rock` / `Mantra`), and an optional `- Gastgeber: <value>[, <value>...]` line naming whoever hosts the evening the song is earmarked for (free text, e.g. `Josua`, or `Josua, Monika` for more than one — comma-separated on the one line, unlike Genre's one-line-per-value), followed by the resource links (YouTube, tabs, tutorials) as plain Markdown link bullets, plus any other aside (e.g. `- Capo: 3. Bund`) that would otherwise float between the H1 and the first H2. The YouTube link is always labelled `[Lied auf YouTube]`; other links are free text (`Source tab`, `Guitar tutorial`, …). `song_tags` in `lib/build_helpers.rb` parses the `Sprache:`/`Genre:`/`Gastgeber:` lines into `[category, value]` pairs, splitting a comma-separated Gastgeber line into one pair per name (other list items — a Capo note, the resource links — are not tags and are skipped); the category is exactly what was written, not inferred from a fixed vocabulary, so a language, genre or host this book hasn't seen before still lands in the right [table-of-contents tag filter](#table-of-contents-tag-filter) control. `validate_song!` **requires** at least one Sprache and one Genre tag, aborting the build otherwise — tagging is not optional; Gastgeber is not required the same way, since not every song needs a host attached.
- An optional **`## Instructions`** section, right after `## Infos über das Lied`, holds alternate chord fingerings (e.g. a capo shape or a barré alternative) as a plain code block, same as the [chord tooltip](#keyboard-and-dialogs)'s guitar tab.
- `merge_about_section` in `lib/build_helpers.rb` splices `## Instructions` into `## Infos über das Lied` at build time — the source file keeps them as two sections (above) for readability; nothing else on disk needs to change when editing a song. This merged section is stripped from `print.html` entirely (tags, resource links and alternate fingerings are all screen-only features) — see [`spec/fixtures/golden/infos_ueber_das_lied.html`](spec/fixtures/golden/infos_ueber_das_lied.html).
- `content/Introduction.md` is always prepended as the first slide

## Chord rendering pipeline

The Ruby script transforms `[Chord]` markers before passing to Pandoc:

```
[C] → `C`{.c}    (CSS class = lowercase first letter)
[Am] → `Am`{.a}
[G7] → `G7`{.g}
```

Pandoc renders these as `<code class="a">Am</code>` etc. CSS in `style/shared.css` assigns a distinct color per chord letter (A=red, B=gray, C=blue, D=green, E=yellow, F=violet, G=brown). In `index.html` (not `print.html`), `chord_buttons` (`lib/build_helpers.rb`, in `post_process_index`) then wraps each one in a real button — `<button type="button" class="chord"><code class="a">Am</code></button>` — see [Keyboard and dialogs](#keyboard-and-dialogs). Only classes `a`–`g` and `x` are wrapped, the ones `chords.js` has a fingering for.

The regex only matches `[Word]` not followed by `(` — so standard Markdown links `[text](url)` are left untouched.

## Shared pipeline

`build` and `spec/support/fixture_builder.rb` run the same code, in `lib/build_helpers.rb`: `songbook_markdown` (front matter with `lang: de-CH`, the introduction, the songs with their chords marked up), `pandoc!`, `post_process_index` and `post_process_print` (both of which call `split_song_artist`, see [Song file format](#song-file-format)). What differs is a parameter — `assets:` (`style/` beside `index.html`, `/style/` for the fixtures served from `spec/fixtures/`) and the multiplex config. Change the pipeline there, not in one of its callers.

## Table of contents tag filter

The TOC can be filtered by Sprache (language), Genre and Gastgeber (host). Each song's tags live in its `## Infos über das Lied` section (see [Song file format](#song-file-format)); the build carries them into the TOC and `style/toc-filter.js` wires the interaction:

- `song_tags` parses the `Sprache:`/`Genre:`/`Gastgeber:` list items of each song's `## Infos über das Lied` section into `[category, value]` pairs. `build` and `fixture_builder` collect one such array per song — in the same order the TOC lists them — and pass it to `post_process_index` as `tags:`.
- `inject_toc_filter` (a Nokogiri pass, like `wrap_slide_content`) first turns Pandoc's TOC `<ul>` into an `<ol>` and drops its first `<li>` — the Introduction, which isn't a song and carries no tags — entirely, rather than merely excluding it from the filter; the remaining `<li>`s then line up with `tags[i]` **by order**, not by re-deriving Pandoc's slugs. It adds `data-sprache="Englisch"` / `data-genre="Pop"` / `data-gastgeber="Josua,Monika"` attributes to each one and prepends a `<fieldset id="toc-filter">` (a `.visually-hidden` legend „Filter" — the Sprache/Genre labels next to the selects, and Gastgeber's own visible label, already say what's being filtered on-screen, so the outer legend only needs to reach a screen reader) holding one `<select>` each for Sprache/Genre (single-choice; `toc_filter_select`, sorted, first option „Alle") that has at least one tag, a `<div class="toc-filter-field toc-filter-checkboxes" role="group" aria-label="Gastgeber">` of checkboxes for Gastgeber (`toc_filter_checkboxes`, one per distinct host, sorted — multi-choice rather than a select, since more than one host's songs are often worth seeing at once; a `role="group"` `<div>` rather than a nested `<fieldset>`/`<legend>`, which both Chrome and Firefox still render as its own line even inside a flex fieldset and so inflated the whole bar's height — see [decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md](decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md)) if any song has one, and a „Reset" button, plus a `<p id="toc-filter-empty" class="toc-hidden">Keine Ergebnisse, bitte Filter anpassen</p>` after the list for `toc-filter.js` to reveal when a filter leaves nothing standing. With no tags anywhere, neither the fieldset nor that message is added (only the `<ol>`/Introduction-removal step still runs).
- `style/toc-filter.js` re-renders on every `change` and hides the `<li>`s that don't match (`.toc-hidden`, also toggled on `#toc-filter-empty` but inverted — shown only once nothing else is). Sprache and Genre combine with **AND** (a song must match the selected Sprache *and* the selected Genre, for whichever of the two has a selection); Gastgeber's checkboxes combine with **OR** among themselves (a song matches if it names *any* checked host), then **AND** into the rest — see [decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md](decisions/2026-10-05-gastgeber-filter-uses-checkboxes-not-a-select.md). „Reset" clears every control; untagged entries hide while any filter is active. The selects, checkboxes and the Reset button are real form controls, so the `keyboardCondition` in `body-controls.html` already keeps their keys (Space, arrows, Home/End — reveal.js's own guard only excludes input/textarea, not select/checkbox) from reaching Reveal. The selection is local to each client and is **not** synced over multiplex.
- Styling: fieldset/select/checkbox/button layout, the `<ol>`'s constant ~90% width and its `<li>` title truncation (`overflow: hidden; text-overflow: ellipsis`, so a title wider than that box shortens with „…" instead of wrapping or stretching the box) all live in `shared.css`; colours and the sticky bar in `night.css` (with a bright-mode override). The bar is `position: sticky; top: 0`. Reveal's `display: 'flex'` config (`post_process_index`) makes every present slide, `#TOC` included, a flex container — flex's default `align-items: stretch` would otherwise cap `.slide-content` at `#TOC`'s own (viewport) height instead of its full, much taller, content height, and a sticky element only sticks within its containing block, so past that cap the filter bar would just scroll away with everything else instead of staying put. `section#TOC > .slide-content { align-self: flex-start }` (`night.css`) is what actually keeps it visible while the list scrolls underneath it — see [decisions/2026-10-04-toc-filter-sticky-broke-past-one-screen-of-flex-stretch.md](decisions/2026-10-04-toc-filter-sticky-broke-past-one-screen-of-flex-stretch.md).

The golden `spec/fixtures/golden/toc.html` pins the generated markup; `spec/unit/song_tags_spec.rb` covers the parser, `spec/integration/golden_html_spec.rb` the injected markup and the print stripping, and `spec/browser/toc_filter_spec.rb` the interaction (including a real past-one-screen scroll, which is what actually exercises the sticky fix above).

## Tests

```bash
npm install --prefix multiplex-server   # once; needs Node.js >= 18
bundle exec rspec
```

`spec/support/fixture_builder.rb` builds `spec/fixtures/index.html` and `print.html` from the songs in `spec/fixtures/songs/` at the start of the run (they are gitignored, not committed). The browser specs serve them with WEBrick on `127.0.0.1` and a port the OS picks (`spec/support/file_server.rb`), so a second checkout's run does not collide with it.

**The specs never touch the live multiplex channel.** `spec/support/multiplex_server.rb` runs `multiplex-server/` — the official reveal-multiplex package, the same software the public Railway server runs, pinned by commit — on `127.0.0.1:18889` (`localhost.js` keeps it off the LAN) for the whole run. The fixture points at it with a fixed test pair (`sha256(secret) == socketId`, which is all the server checks). Before, the fixture carried `multiplex-token.json`, so the „live sync" spec became master on the channel songs.josh.ch listens to, and moved anyone who had it open at the time. Port and token are fixed rather than fresh per run so that the committed fixture stays the same from run to run. They refuse to start while port 18889 is taken (a multiplex server left over from a manual test, say): their own would die on `EADDRINUSE` while the other one answered the readiness check, and the specs would broadcast into it.

Nothing leaves the machine during a run: the fonts are local too (see below). The slide-zoom expectations are exact values measured with those fonts, so they also catch a font that renders differently. The one exception is the title slide, whose emoji Chrome lays out differently across its own builds: its exact scale holds locally but is only range-checked on CI (see [emoji zoom is not reproducible across Chrome builds](decisions/2026-09-30-emoji-zoom-is-not-reproducible-across-chrome-builds.md)).

`bundle exec rake golden:update` regenerates the golden snapshots in `spec/fixtures/golden/` after an intended markup change.

**CI runs the whole suite on every pull request, and on every push to `master`** (`.github/workflows/test.yml`): Ruby 3.2, Pandoc pinned to the same 3.9.0.2 the golden fixtures were built with, the `multiplex-server/` dependencies via `npm ci`, then `bundle exec rspec`. `push` is deliberately scoped to `master` only — left unscoped, a branch with an open PR would run the identical suite twice on every commit (`push` and `pull_request` both fire); `master` still needs its own `push` trigger since the deploy job's `needs: rspec` depends on an `rspec` run from that same push-triggered workflow (merging a PR doesn't re-fire `pull_request`). `Gemfile.lock` carries `x86_64-linux` alongside `arm64-darwin` so the Linux runner resolves nokogiri's native gem — regenerate both platforms with `bundle lock --add-platform x86_64-linux` if you ever relock.

**Cold-boot retry:** headless Chrome cold-starts on the first browser example of a run, and on a loaded runner that launch handshake used to occasionally exceed `process_timeout` and fail the whole run (and the deploy) with `Ferrum::ProcessTimeoutError: Browser did not produce websocket url …` — not a real assertion, just a flaky launch. A `prepend_before(:each, type: :feature)` hook in `spec/spec_helper.rb` now forces the browser up and, on a boot timeout, quits the dead process and retries the launch (up to three attempts), so a flaky cold start no longer reddens the run. If a `ProcessTimeoutError` still surfaces, the launch failed three times running — treat that as a real environment problem (missing browser, starved runner), not a re-run.

## Vendored reveal.js

`style/revealjs/` holds reveal.js **6.0.2** — only the five files the pages load (`dist/reveal.js`, `reveal.css`, `reset.css`, `theme/night.css`, `theme/serif.css`) plus its `LICENSE`. Everything under `style/` is deployed, so the rest of the release (tests, demo, other themes, `package-lock.json`) stays out. The paths match Pandoc's `revealjs-url`, which is why the `dist/` folder is kept.

To upgrade, copy those five files from `dist/` at the release's tag in the Git repository (`https://raw.githubusercontent.com/hakimel/reveal.js/<tag>/dist/…`), remove the two Google Fonts `@import`s from the start of `theme/night.css` again, rebuild and run the specs. Pandoc's template also loads the notes, search and zoom plugins from their reveal.js 5 paths; the song book uses none of them, and `build` removes those script tags.

6.0.2 is the minimum: it makes every slide but the current one `inert` ([hakimel/reveal.js#1587](https://github.com/hakimel/reveal.js/issues/1587)). With 6.0.1, `Tab` on the Introduction reached the table of contents' links, which reveal.js keeps rendered next door but invisible — 35 of 40 presses landed there.

**Fonts:** `style/fonts/` holds Montserrat 700 and Open Sans (400/700, with italics) as Google Fonts serves them — 25 woff2 files, every subset, with their OFL licenses — and `fonts.css` with Google's `@font-face` rules pointing at them. `post_process_index` links it; the night theme's own `@import`s from fonts.googleapis.com are removed, so no visitor's browser asks Google for anything.

`style/qrcodejs/` holds qrcodejs 1.0.0 (the 🔗 dialog's QR code) with its `LICENSE`, served from the song book itself rather than jsDelivr.

## Slide layout and fit

Reveal's own `center: true` only centers a slide **among its siblings inside a `.stack`** (`section.stack { flex-direction: column; justify-content: center }` in `shared.css`) — a song or the Introduction, which have sub-slides, gets this for free. `section.deck-title-slide` has no sub-slides, so Pandoc never wraps it in a `.stack`, and it needs its own rule (`shared.css`) to center vertically. That rule uses `align-items: center`, not the flex default `stretch`: `style/slide-zoom.js` measures `.slide-content`'s natural (shrink-to-fit) width to decide how far it can scale up, and a stretched-to-100%-width box always measures as already full, capping the scale at 1 instead of the ~1.4 the title actually fits.

**Every rendered slide is fitted, whenever its size could change.** `slide-zoom.js` scales each slide's `.slide-content` (on the title slide, the Introduction and every song slide, i.e. all but the TOC) with `transform: scale()`, by its natural size against the room on screen. A `ResizeObserver` watches every one of them, the deck (`.reveal`, i.e. the window) and the right chevron. A slide's own entry re-fits that slide, and the deck's or the chevron's re-fits them all. The deck, not `<html>`: the two are the same box except during [Vollbild](#vollbild) on an iPhone, where `<html>` is many screens tall and doesn't change as Safari's bars come and go. Observer callbacks run after layout and before paint, so a slide is fitted in the very frame it appears, whether Reveal shows it next to the current one, the overview shows dozens at once, the fonts arrive, or „Akkorde anzeigen" changes its line widths. There's no list of events to keep up to date.
- **Why a transform, not CSS `zoom`:** a transform leaves the layout alone, so the observer sees the natural size and the scaling never sets it off again. `zoom` re-wrapped the text at another width than was measured.
- **No unfitted frames:** until its first fit, a slide's content is `visibility: hidden` (`night.css`, with a 1s animation that shows it anyway should the script never run). A reload shows a blank slide for a moment, never one at the wrong size. `post_process_index` loads `slide-zoom.js` before the socket.io script, which comes from the relay's host and could hold it up.
- **Title slides by their widest line:** a title slide (the deck's own, the Introduction's, every song's — `TITLES` in `slide-zoom.js`) holds nothing but lines of text, and is measured by the widest of them (a `Range` over each child's contents), not by its box. A title too long for one line wraps, and its box then takes the whole width while its lines fall short of it: measured by the box, a song's title on an iPad in portrait stayed at scale 1, a third short of the edges. Lyric slides need none of this: they are `white-space: nowrap`, so their box is their widest line. See [a wrapped title is fitted by its widest line](decisions/2026-10-28-a-wrapped-title-is-fitted-by-its-widest-line.md).
- **A title takes as many lines as make it largest:** on one line, a long title fills the width of a wide screen and leaves most of the height empty (three quarters of it on an iPad in landscape). `wrapTitles` (`slide-zoom.js`) measures the heading's words once on a single line, works out the narrowest split into 1, 2, 3, … lines from where they stand, predicts each one's scale against the room, and sets the winner as the heading's `max-width` (`shared.css` centres the heading and balances its lines with `text-wrap: balance`). The best count depends on the title *and* the screen's shape: „Imagine (John Lennon)" takes three lines on a 1280×800 desktop, two on a phone held sideways, where a third would cost more height than it saves width. One line is always a candidate, so no title comes out smaller than unwrapped. Rewrapping changes the content's size after the observer reported it; it would report it again in the same frame and Chrome raises „ResizeObserver loop completed with undelivered notifications", so a rewrapped content is unobserved and observed afresh from the next frame. Lyrics never wrap: a line of lyrics is a musical phrase, its chords placed within it. See [a title takes as many lines as make it largest](decisions/2026-10-28-a-title-takes-as-many-lines-as-make-it-largest.md).
- **Overview:** the overview gives every slide the full screen height (`.reveal.overview .slides section { height: 100% }`). The fitted contents are `align-self: center` (`night.css`) so they keep their natural height there instead of stretching to it, which capped every overview slide at 1.
- **Chevrons:** the room is the window minus a gutter on each side as deep as Reveal's chevrons reach in (see [Desktop navigation](#desktop-navigation-chevrons)). That's the side chevrons' depth on the left and right, and the up/down ones' at the top and bottom, measured from their layout offsets, not `getBoundingClientRect` (Reveal slides the chevrons in and out with a transform). Where the chevrons are hidden, they measure 0 and the content gets the whole screen.
- **Side effects:** `chords.js` multiplies a chord's computed font size by this scale (rendered box over layout box) to size its tooltip, since `getComputedStyle` leaves a transform out.

See [slides are fitted by a ResizeObserver, with transform: scale()](decisions/2026-10-28-slides-are-fitted-by-a-resizeobserver-with-transform-scale.md).

## Next-line preview

**Every sung sub-slide of a song ends on a preview of what comes next**, so whoever scrolls can read ahead and is never late: „Next:", the next sub-slide's heading, „-" and its first line, chords included, then „..." („Next: **Chorus** - I was the [Am] one who let you [C] know..."), or „Ende des Lieds" on the song's last sub-slide. `inject_next_line_previews` (`lib/build_helpers.rb`, in `post_process_index` before `wrap_slide_content`) appends a `<p class="next-line">` to each `section.level2` of every song but its „Infos über das Lied" slide. Neither that slide nor the song's own title slide gets one (nothing is sung there yet), nor does the Introduction (the first stack, skipped by order like in `inject_toc_filter`), nor `print.html`. The "first line" (`first_line`) is the next slide's first block after its heading, up to the first `<br>`; Pandoc's soft wraps become spaces.

- **Layout:** it sits inside `.slide-content`, below the lyrics, so `slide-zoom.js` fits it together with them. `shared.css` sets it at 0.6em under a rule. It never wraps, like the lyrics: a preview wider than the lyrics widens the slide, and the whole slide is fitted to it (a short Intro or Interlude gets smaller for it). It keeps the lyrics' colours, and its heading (bold) the slide titles' (`night.css`, with a bright-mode override). It is dimmed by its opacity alone, which never gets past 60%. Only the separating rule has a theme colour (`night.css`, with a bright-mode override).
- **It fades in late, and doesn't snap away.** It is only needed toward the end of a slide, so it stays out of the way at first. When its slide becomes the current one (Reveal's `.present`), the preview is fully transparent for 3 s, then fades in slowly to 60% over another 3 s. Every visit starts over. „Ende des Lieds" has nothing to read ahead and shows at 60% at once. Leaving, it keeps whatever opacity it had while Reveal moves and fades the whole slide out (0.8 s, `transitionSpeed: 'default'`), and is reset only after that. These are CSS transitions in `shared.css`, not an animation, which would end the instant `.present` goes. `@starting-style` makes a slide shown straight from `display: none` (a jump, the first load) start from transparent too. A chord in the preview that takes the focus (`:focus-within`) shows it at once, so the focus never sits on something invisible. Cuprite counts `opacity: 0` as invisible, so a spec that clicks or reads the preview first calls `finish_next_line_fade` (`spec/spec_helper.rb`).
- **It is ordinary content.** Screen readers read it too: in a live-scroll session a follower cannot move on to read ahead (and reveal.js keeps the other slides `inert`). Its chords are chord buttons like any other (Tab stops, fingering on click); hiding the chords in ⚙️ hides these with the rest. `inject_next_line_previews` runs before `chord_buttons`, which wraps these copies along with the rest. `chords.js` sizes a preview chord's fingering as if the chord were set at the lyrics' size, not at the preview's 0.6em. A spec that looks up a chord by its text across the deck must mind these copies, which come *before* the next slide's own chords in the document.

The golden `spec/fixtures/golden/imagine_verse1.html` pins the markup, `spec/unit/next_line_preview_spec.rb` the extraction, `spec/browser/index_html_spec.rb` the single line (slide zoom) and the fade (next-line preview), and `spec/browser/chord_tooltips_spec.rb` its chords. See [decisions/2026-10-28-each-song-slide-previews-the-next-line.md](decisions/2026-10-28-each-song-slide-previews-the-next-line.md).

## Desktop navigation: chevrons

**Reveal's chevrons show on a desktop, at the screen edges.** Pandoc's `controls: true` is kept, and `post_process_index` switches `controlsLayout` to `'edges'`: ‹ › at the left/right middle, ˄ ˅ at the top/bottom centre, clear of the four corner buttons (the default bottom-right cluster sits exactly where 🚀 is). `night.css` hides them under `@media (pointer: coarse), (width < 500px)`: a touch screen swipes instead, and below 500px reveal.css drops the edges layout and falls back to that bottom-right cluster. It is not gated on `(hover: hover)`, because headless Chrome on the Linux CI runner reports no hover and would hide them on the "desktop" the specs test. During a live-scroll session `applyNavMode` turns them off for the scroller and the followers, and back on once the session ends.

**A trackpad swipe or the mouse wheel does not page the deck.** Reveal only handles swipes from a touch screen; a trackpad sends `wheel` events instead. Paging on those was built and then dropped: telling a swipe's momentum tail from the next swipe needs guesswork about the deltas (no web API exposes the trackpad's own phases), and it never felt reliable on a real MacBook. The chevrons and the arrow keys are the desktop's way through the book. See [desktop chevrons at the edges, no trackpad paging](decisions/2026-10-28-desktop-chevrons-at-the-edges-no-trackpad-paging.md).

Pandoc itself gives this slide `id="title-slide"` and nothing else; `rename_title_slide_id` (`lib/build_helpers.rb`, the first step of both `post_process_index` and `post_process_print`) swaps that for `class="deck-title-slide"` before anything else runs. reveal.js's Location plugin builds the URL hash from the current slide's id, so the id, left alone, pinned `#/title-slide` into the address bar forever after the slide was first shown — a plain `index.html` URL never came back. Every selector that targets this slide, in CSS or JS, must read `section.deck-title-slide` (the element type, not a bare class): reveal.js copies a slide's classes onto its `.slide-background` div too, and a bare `.deck-title-slide` would also catch that. See [decisions/2026-10-05-title-slide-id-replaced-with-a-class.md](decisions/2026-10-05-title-slide-id-replaced-with-a-class.md).

## Keyboard and dialogs

**The URL is written the moment the page is hidden** (`visibilitychange`): Reveal writes it at most once a second, and iOS stops that timer in the background, so a phone that switched apps right after a slide change and was discarded there reloaded a slide early.


**The controls sit in four corners, one in each.** Top left: 📖 jumps to the table of contents (hidden while a live-scroll session locks this device's navigation — see Multiplex below). It's a link to `#/1`, but a click goes by `Reveal.slide` (`gotoToc`) instead of following it: a navigation leaves an entry in the history, and on an iPhone in [Vollbild](#vollbild) Safari showed its bars again after one. Reveal's own paging writes the URL with `replaceState`, which Safari lets be. A click with a modifier key still opens the link, in a new tab, say. Top right: ↕️ toggles [Vollbild](#vollbild). Bottom left: 📡 opens the live-scroll dialog, a badge on its corner saying this device's role at a glance; the dialog holds 🚀 (start or end a session) and 🔗 (the QR code), which used to be corner buttons of their own (see Multiplex below). Bottom right: ⚙️ opens the settings. Reveal's own chevrons sit at the screen edges between them, on a desktop only (see [Desktop navigation](#desktop-navigation-chevrons)). On a phone (`width < 500px`) the dialogs take a smaller font and margins, or the live-scroll dialog ran off the bottom.

**The overlays are native `<dialog>`s** (in `style/body-controls.html`), opened with `showModal()`. 🚀 leads through up to two — the password prompt (focuses its field), then the „wer scrollt?" choice, and on the clients the guest invitation (guest mode); self mode announces the coming song as a toast instead (see [Self-scroll announcement](#multiplex-live-sync) below), not a dialog. ⚙️ opens a settings dialog (a theme `<select>` — „Dunkel"/„Hell", more to come — and an „Akkorde anzeigen" checkbox); the multiplex status button opens a dialog with the connection/role status spelled out in words. The QR, choice, invite, settings and multiplex-status dialogs all focus their title (`tabindex="-1"`, no ring), so a screenreader starts there and a phone shows no keyboard. Two things `showModal()` leaves to us, for every dialog: Reveal listens for keys on the document, where they still arrive from inside a dialog — so each dialog stops `keydown`/`keypress` from propagating, or the arrow keys would page the deck behind it and Esc would open Reveal's overview — and a click on the backdrop lands on the `<dialog>` itself, which closes it.

**Space on a focused button presses that button, and only that** (`keyboardCondition`, set with `Reveal.configure` on load): Reveal used to turn the page as well, so Space after 🚀 both ended the session and moved on. The exception is a focus nobody can see: a mouse click leaves the button focused without a ring, and there Space blurs it and turns the page, as the one clicking expects. Whether the ring shows is read on `focusin`, because Chrome turns `:focus-visible` on as soon as any key is pressed. Inside a `<dialog>` this doesn't come up at all — the dialog stops the keydown before Reveal ever sees it, so Space on the settings checkbox or select just does the native thing.

**The buttons' labels are their tooltips.** Each control's `.visually-hidden` text is shown as a tooltip on hover (only where there is hover, `(hover: hover)`, so a tap on a phone shows nothing) and on keyboard focus. Esc hides it without opening Reveal's overview, any other key hides it too, and it stays hidden until the pointer leaves or the focus moves.

**Chords are real `<button>`s** (`chord_buttons` at build time, `style/chords.js` for the fingering), the copies in a slide's [next-line preview](#next-line-preview) included. The `<code>` inside is the coloured pill; the button shows nothing of its own (`all: unset` in `shared.css`), so the focus/hover ring is drawn around the pill. Tab, Enter and Space are the browser's own: Enter or Space opens the fingering, and the tooltip is read out as it appears (`aria-live`); `chords.js` only adds `aria-expanded`/`aria-controls`. Space on a chord focused by a mouse click turns the page, like on any button (see above). Hiding the chords in ⚙️ hides the buttons too, so they leave no empty Tab stops. The tooltip shows the guitar tab (`|E A D G B e|`, preferring a song's own Instructions legend over the built-in `DEFAULT_CHORDS` fallback) beside a ukulele tab (`|G C E A|`, standard re-entrant tuning) from the separate `UKULELE_CHORDS` dictionary — side by side rather than stacked, since a slide has more spare width than height. The chord name only appears once, on the guitar column's own `Name |…|` row; the ukulele column (no per-song override — songs never document their own ukulele voicing) is just `|…|`, and a chord missing from `UKULELE_CHORDS` falls back to a single guitar-only column.

**Storage is optional:** with site data blocked, touching `localStorage` or `sessionStorage` throws, so every access is wrapped; the theme then switches without being remembered.

## Vollbild

**↕️, top right, toggles full screen; a second press leaves it.** Where the browser has the Fullscreen API (a desktop, Android, an iPad: `document.fullscreenEnabled`, or its `webkit` form), ↕️ uses it on `<html>`, and `aria-pressed` follows `fullscreenchange`. While on, ↕️ wears a ❌, to say a press now leaves full screen. Started from the home screen (`navigator.standalone`, `display-mode: standalone`), the book has no bars to hide, and ↕️ stays hidden.

**On an iPhone, ↕️ asks for a swipe instead.** Safari there has no Fullscreen API for a page, but it hides its bars once a finger scrolls the page itself, which never happens in the deck: the page is one screen tall, and `.reveal` has `touch-action: pinch-zoom` (Reveal 6 reads swipes from pointer events, whose `preventDefault` stops no scrolling, so the CSS is all that does). So ↕️ opens the runway (`#fullscreen-runway`, `body-controls.html`):
- `html.fullscreen-runway` (`night.css`) lifts Reveal's `overflow: hidden`, pins `.reveal` with `position: fixed`, and the runway over it makes the page many screens tall: „Wisch mal runter!", with arrows on the way. Its title and ✕ sit in a sticky header, so ✕ stays at hand while the page scrolls. Its first screen is `100svh` high, the height with Safari's bars shown, so its last lines don't end up under the bottom bar.
- When the bars go, the window gets taller (`innerHeight`, read on `resize`, `scroll` and `visualViewport`'s `resize`). A 🎉 says so („Gut gemacht! …") and waits for OK (or Esc); a swipe on it doesn't scroll the page (`touch-action: none`), so all of it has to fit one screen, an iPhone SE's included. Only then does it show the alternative: from the home screen the book opens without any bars, with a picture of Safari's menu (`style/zum-home-bildschirm.png`, loaded lazily, so only by those who open the runway). Its `src` reads `{{assets}}zum-home-bildschirm.png`: `post_process_index` replaces `{{assets}}` in `body-controls.html` with the same `assets:` prefix as the other files, since the build and the spec fixtures serve `style/` from different paths. Then the runway fades out, but **it keeps its height and the scroll position**: a page back to one screen would scroll to the top, and Safari would bring its bars right back. Back in the deck, nothing may scroll the page, so the bars stay away. Reveal's keys don't, and on the deck `touch-action` keeps the fingers off it, but it reaches neither a code block (Reveal's theme gives `pre code` `overflow: auto`, a scroll container of its own) nor the corner buttons beside the deck: a swipe down there scrolled the page up, and the bars came back. So while the room is kept, `holdPage` cancels every one-finger `touchmove` on the document, except in the table of contents or a dialog that holds more than fits; those two get `overscroll-behavior: contain` meanwhile (`night.css`), so a swipe past their ends stays with them.
- A second press of ↕️, the bars coming back (a tap on Safari's address strip) or a turned phone (another width) give the room back. A pinch-zoom shrinks `innerHeight` too and is ignored (`visualViewport.scale`). Esc or ✕ close the runway before the swipe; like the dialogs, it keeps its keys from Reveal.
- `?runway` in the URL forces the runway in any browser, to try it on a desktop, and for the specs.

The fit follows: `slide-zoom.js` watches the deck, not `<html>` (see [Slide layout and fit](#slide-layout-and-fit)). `spec/browser/index_html_spec.rb` (`Vollbild`) covers both ways, with a taller window standing in for Safari's bars going. See [the iPhone's Vollbild swipes the page itself](decisions/2026-10-28-the-iphones-vollbild-swipes-the-page-itself.md).

## Multiplex (live sync)

The presentation uses the [Reveal.js multiplex plugin](https://revealjs.com/multiplex/) via `multiplex.up.railway.app` so that the audience can follow along on their own devices. It is not a running mirror of the presenter's every move: the presenter opens a **live-scroll session** on one song, and either scrolls it or hands the scrolling to a guest for that song.

The code is the second `<script>` in `style/body-controls.html`; the server is a pure relay (one event, `multiplex-statechanged`, forwarded to everyone but the sender when `sha256(secret) == socketId`, no storage). Three message types ride on that one event: `session` (from the presenter), `state` (from whoever scrolls) and `volunteer` (from a guest offering). `body-controls.html` is spliced in *after* the build's `keyboard:`/`controls:` rewrites (see `post_process_index`), so its own `Reveal.configure` calls are not mistaken for Pandoc's init.

- **The presenter is the single authority.** 🚀 (in the 📡 dialog, enabled only while the current slide is a song; elsewhere it is disabled, with a hint saying why) asks for the password once per tab (`sessionStorage` `multiplex-presenter` holds `authed`, the `claim` and the live session, if any), then opens a choice: „Ich selber möchte scrollen" or „Ein Gast soll scrollen". Once entered, the password is never asked again on that tab — `authed` is persisted independently of whether a session happens to be live at the moment, so it survives a reload between sessions too, not just mid-session. Only the presenter opens a session, names the scroller and closes it; 🚀 then reads „Live-Scrollen beenden" (and stays enabled throughout the session — the scroller is always on a song — so it can be ended). 🚀 and 🔗 close the 📡 dialog before opening their own, so the focus returns to 📡 afterwards. Another presenter with a higher `claim` (a duplicated tab settles by `from`) makes this one step down — the only leaderless bit left.
- **Every role survives a reload, not just the presenter's.** `senderId` — normally a fresh random value per page load — is itself kept in `sessionStorage` (`multiplex-sender-id`), so a reloaded guest scroller is still recognised as the same `scrollerId` the presenter already named, instead of coming back as a stranger and dropping to a mere follower. A non-presenter's last known session is separately cached (`sessionStorage` `multiplex-session`, written in `reconcileSession`/`concludeSession`/`releaseSilently`) and reapplied immediately on load, before the next heartbeat would otherwise re-establish it — so a follower or a scroller doesn't flash back to free navigation for the few seconds in between.
- **Guest delegation.** In guest mode every client is asked „«Song» wird als nächstes gespielt. Möchtest du das Live-Scrollen übernehmen?". The first „Ja" the presenter hears wins — it echoes the chosen `scrollerId`, the other invites close, and everyone (the presenter included) follows the guest. A single authority means two near-simultaneous „Ja"s cannot both take over. The moment a scroller is named, whoever had been invited for that session (`invitedFor`, `volunteeredFor` in `reconcileSession`) gets a one-off toast on `#multiplex-toast`: the winner „Danke für deine Bereitschaft! Lass uns gleich starten…", a volunteer who lost the race „Oh, das wäre nett gewesen – aber jemand anderes scrollt bereits!", and everyone else who was asked but didn't win (declined or never answered) „Es geht gleich los!". The presenter gets its own toast the instant it accepts a volunteer — „Jemand hat sich bereit erklärt, es geht gleich los" — instead of a silent status-line change. A latecomer who was never invited sees none of these.
- **Self-scroll announcement.** In self mode the presenter scrolls, so there is nothing to volunteer for; each client that is present as the session opens is shown a toast on `#multiplex-toast` — „Es geht gleich los!" / „Der nächste Song ist «Song»." (once per session, `announcedFor`) — and then follows along, same as any other toast: no OK button, it just fades after its own timeout. The opening `session` carries `fresh: true` and the heartbeats do not, so a latecomer who only ever hears a heartbeat just follows — as with the guest invite. The presenter sees no such toast.
- **The scroller is locked to its song** (`SCROLLER_KEYS` disables the horizontal keys plus Home/End — reveal.js binds those to "next slide"/"first slide"/"last slide", which reached the snap-back below too, but only after already jumping and losing the scroll position (v reset to 0). Space/Shift+Space default to the same escape-prone `next()`/`prev()`, so `SCROLLER_KEYS` remaps them instead of disabling them outright: they call `Reveal.down()`/`Reveal.up()`, the same calls the (already safe) vertical arrow keys make, stepping within the song and no further. A capture-phase guard swallows horizontal *swipes* before Reveal sees them — Reveal has no vertical-only touch option, so this keeps vertical scrolling while a left/right swipe does nothing; a link that still leaves the song snaps back on `slidechanged`). It may only scroll up/down within the current song; to move on, the presenter ends the session.
- **Everyone else follows, with no opt-out.** A follower's keyboard, touch and controls are off and its view is snapped to the scroller — there is no more „browse freely" (👣 is gone). 📖 is hidden too, for the scroller as well as every follower (`applyNavMode`): without it, clicking through to the TOC would still be undone by the `slidechanged` snap-back, but not before an unwanted flash. A follower that hears nothing from the session for three heartbeats frees itself rather than freeze; the presenter's next heartbeat locks it again. The presenter is exempt from this self-release, even though it is itself a "follower" of a guest it delegated to: a flaky connection to the *guest* used to silently eject the presenter from its own session three heartbeats later — the ❌ vanished and 🚀 reverted to „Live-Scrollen starten" — while the guest, and everyone else still locked to it, carried on regardless, now with nobody able to end it. See [the presenter must not self-release while following its own delegate](decisions/2026-10-04-presenter-must-not-self-release-while-following-its-own-delegate.md).
- **Heartbeat:** the presenter repeats the `session` and the scroller its `state` every 2 s (`HEARTBEAT_MS`; the specs shorten it through `window.MULTIPLEX.heartbeat`), and again right after a reconnect. That is how someone who opens the page mid-session, or comes back from a dead spot, catches up — the relay hands out no last state. A latecomer who arrives while a guest is still being sought is invited too; once a scroller is named, latecomers just follow.
- **Only the slide is sent** (`stateToSend`): indices, never `overview` or `paused`. While the scroller browses the overview, the slide it was opened on is repeated.
- **Ending the session** drops everyone — the presenter included — back onto the table of contents (`gotoToc`, the `#TOC` slide) and shows a toast (`#multiplex-toast`, `aria-live`): „Du kannst jetzt wieder frei navigieren" to everyone who was in it, and „Vielen Dank fürs Scrollen!" on top of that for the guest who scrolled. A silent timeout (lost connection) frees a follower where it stands, without the jump. The `active: false` broadcast that announces the end is repeated twice more over the following second (`endSession` in `body-controls.html`) — it is the one message a dropped heartbeat never covers, since there is no more session to heartbeat once the presenter thinks it is done, so a single lost packet used to strand everyone else until their own three-heartbeat timeout freed them.
- **Status button** (📡, bottom left, `#multiplex-status-button`): a graphical, role-aware stand-in for what used to be a floating text line — inspired by the sibling project `axipedia`'s multiplex "lamp" (`revealjs/plugin/multiplex/multiplex.js` there). A badge on the 📡's corner says who's driving at a glance: a filled dot when this device moves the deck for everyone (self-scroll presenter, or a guest scrolling for the room), an open ring when it's locked to someone else's scroll instead (an ordinary follower, or the presenter after delegating to a guest), amber while a presenter waits for a guest to volunteer, grey when idle, and a diagonal strike over whichever shape applies when the socket itself is disconnected — colour is never the only signal (WCAG 1.4.1), matching axipedia's own reasoning for the same choice. A click opens the live-scroll dialog, with the same state spelled out in words, above 🚀 and 🔗. That text — „Du scrollst live" / „Warte auf Gast …" / „Gast scrollt" for the presenter, „Du scrollst für alle" for the guest, „Folgt" for a follower, „Keine Verbindung" for a dropped connection, „Kein Live-Scrollen aktiv" otherwise (`statusText()`) — also sits, invisibly, as the button's accessible name (`#multiplex-status`, `role="status"`, `.visually-hidden`) for a screenreader to announce as it changes. It is the ongoing truth, for as long as a condition lasts; `#multiplex-toast` layers the *moment something changes* on top, for anyone actually in a session: „Verbindung verloren" / „Wieder verbunden" on the socket's own `disconnect`/`connect` events, and — presenter only, since it no longer self-releases (above) — „Keine Rückmeldung vom Gast mehr – du kannst die Sitzung bei Bedarf beenden" the moment the delegated guest goes stale, „Der Gast ist wieder verbunden" once it resumes. The watchdog driving the guest-silence pair ticks on a fixed 500ms, independent of `cfg.heartbeat` — a spec shortening the heartbeat to test it must keep 3× that comfortably above 500ms, or "fresh again" is never observable (`body-controls.html`).
- **QR code** (🔗, in the 📡 dialog): shows a QR code of the current URL so new people can join.

See [decisions/2026-09-30-live-scroll-sessions-presenter-delegates-to-a-guest.md](decisions/2026-09-30-live-scroll-sessions-presenter-delegates-to-a-guest.md).

### Token

The `socketId` / `secret` pair is generated offline, never fetched: the relay only checks `sha256(secret) == socketId`, so any self-consistent pair works. `build` resolves it in this order, and **refuses to build if none is found** (no silent network fetch):

1. `MULTIPLEX_SOCKET_ID` + `MULTIPLEX_SECRET` from the environment — the CI deploy generates a fresh pair per run this way.
2. a gitignored `multiplex-token.json` for local builds — create it once with `bundle exec rake multiplex:token` (run it again for a fresh local session).

The file is no longer committed, so a local build never shares songs.josh.ch's live channel. The generator is `BuildHelpers.generate_multiplex_token`.

### Password

Default password: `guitar`. Override with the `MASTER_PASSWORD` env var at build time:

```bash
MASTER_PASSWORD=mypassword ./build
```

The password is embedded in the generated HTML (visible in source). This is intentional — the goal is only to keep the audience from accidentally starting a live-scroll session, not real security.

## Legacy songs

`content/legacy-songs/` holds songs removed from the active set. They are not included in the build.
